# Bulk Catalogue Manager for WooCommerce — agent entry point

Read in this order, then start work: `docs/SPEC.md` (the agreed shared understanding; change it there before changing code), `docs/TICKETS.md` (80 tickets in build order; each ends with tests green), `docs/prototype/index.html` (open in a browser; it is the design the code must match), `docs/SCOPE-2026-09-21.md` (the owner's scoping answers).

## Hard rules from the owner (Wade Beckett)
- Standalone: works on a bare WordPress + WooCommerce site with nothing else installed and zero site-specific code. Edits native WooCommerce product data only, through WooCommerce CRUD classes.
- No dependency on, module for, detection of, or mention of any third-party plugin in code, docs or UI. Per-customer or per-group product access is out of scope permanently. No client names or client fields anywhere.
- Always free, GPL-3.0-or-later, built to WordPress.org directory standards from the first commit (WPCS, translation-ready, no external calls, uninstall cleanup, Plugin Check clean).
- "Beautiful" means simple and easy for a non-technical shop owner. Plain-English labels; never show a raw meta key.
- Variations are first-class. Every bulk write is previewed first, journaled, and reversible.
- Do not ask the owner to define these further. Fix it, do not ask.

## Front-end conventions
- One folder per panel under `assets/src/panels/<panel>/` with an `index.js` default export (so `app.js` imports stay `./panels/<panel>`), its own `style.scss` imported from that index (leave `assets/src/style.scss` to the shell), and tests in `tests/js/<panel>*.test.js`. Adding a panel is one import and one route line in `app.js` and `router.js`, nothing more.
- Data lives in hooks (`use<Thing>()` returning the data, loading, error and a refetch); components render. Every request goes through `assets/src/api.js` (`request()`), never a hand-built URL.
- No hard-coded field or action lists: columns, labels, choices, sort options, edit kinds, groups and actions come from `GET /fields` (`fields`, `actions`, `groups`). Pick a field by what the registry says about it (type, flags), not by key. A key that must be named (a default view preset) lives in one preset module per panel and is ignored when the registry lacks it.
- Every user-facing string goes through `@wordpress/i18n` with the literal domain `bulk-catalogue-manager-for-woocommerce` and a `translators:` comment on each placeholder; `tests/js/i18n.test.js` enforces it. Render values as text (no `dangerouslySetInnerHTML`; `react/no-danger` is an error).
- Tests mock `@wordpress/api-fetch` and route by path; use the real `/fields` snapshot (`tests/Unit/Fields/fields.snapshot.json`) as the registry fixture.
- Accessibility (T75): announce through `panels/categories/announce.js` (`wp.a11y.speak`), progress through `bulk/announce.js` milestones; a dialog or slide-over returns focus to its opener or, when that is gone, to the nearest thing that shows the result; a new screen or state gets an axe-core check and a keyboard-only journey in `tests/e2e/`. The page header lives in `app.js`; a panel reaches it through `ShellContext` (`shell.js`).
- Do not commit `assets/build` from a feature branch or worktree (exception: `codex/exact-selection-plan`, the release candidate, commits its build by the coordinator's instruction): run `npm run build` locally (it must pass the size gate, and `composer test`'s AssetsTest reads the local build), then leave the build out of the commit. The maintainer rebuilds on main after merging, commits the build, and reruns `composer make-pot` (the .pot also scans the build, so its order follows the committed bundle).
