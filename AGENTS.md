# Bulk Catalogue Manager for WooCommerce — agent entry point

Read in this order, then start work: `docs/SPEC.md` (the agreed shared understanding; change it there before changing code), `docs/TICKETS.md` (80 tickets in build order; each ends with tests green), `docs/prototype/index.html` (open in a browser; it is the design the code must match), `docs/SCOPE-2026-09-21.md` (the owner's scoping answers).

## Hard rules from the owner (Wade Beckett)
- Standalone: works on a bare WordPress + WooCommerce site with nothing else installed and zero site-specific code. Edits native WooCommerce product data only, through WooCommerce CRUD classes.
- No dependency on, module for, detection of, or mention of any third-party plugin in code, docs or UI. Per-customer or per-group product access is out of scope permanently. No client names or client fields anywhere.
- Always free, GPL-3.0-or-later, built to WordPress.org directory standards from the first commit (WPCS, translation-ready, no external calls, uninstall cleanup, Plugin Check clean).
- "Beautiful" means simple and easy for a non-technical shop owner. Plain-English labels; never show a raw meta key.
- Variations are first-class. Every bulk write is previewed first, journaled, and reversible.
- Do not ask the owner to define these further. Fix it, do not ask.

## Identifiers (must match SPEC §15)
Slug and text domain `bulk-catalogue-manager-for-woocommerce`; prefixes `bcm_` / `BCM_` / `bcm-`; PHP namespace `BulkCatalogueManager`; REST namespace `bcm/v1`; PHP >= 8.1, WordPress >= 7.0, WooCommerce >= 10.0. UI on `@wordpress/dataviews` bundled via wp-scripts, server-side paged.

REST (T13): every `bcm/v1` route goes through `Rest\Routes::add()` from a `Rest\Controller` listed in `Routes::plugin()` — never call `register_rest_route()` directly (a test scans for it); `add()` skips, with `_doing_it_wrong()`, any route whose endpoints lack a callable, non-`__return_true` permission callback. Permission callbacks live in `Rest\Access`: `can_read` (`manage_woocommerce`, or `manage_options` under administrators only, filtered by `bcm_capability`), `can_write` (plus `edit_products`), `can_manage_terms` (plus `manage_product_terms`), `can_manage_settings` (`manage_options`), and per object `can_edit_object()` / `user_can_edit_object()` (`bcm_cannot_edit`). Build every refusal through `Rest\Refusal` (`create`, `forbidden`, `invalid`): a `bcm_` code, a §4.8 sentence and `data.status` — a test scans for any other `new WP_Error`. `Routes::client_settings()` gives T8 the namespace root and the `wp_rest` nonce. A change to the `/fields` payload must update `tests/Unit/Fields/fields.snapshot.json` deliberately. The wp-env checks for T5 (uninstall), T6 (tables and indexes after activation, idempotent reactivation, a version bump keeping rows) and T13 (anonymous 401, subscriber 403, shop manager 200, the administrators-only flip, a stale nonce 403 `rest_cookie_invalid_nonce`) are still to be verified. Query (T15): `src/Query/Criteria.php` validates and normalises every read request (mode, search, filters, orderby, order, page, per_page 1–100) against the field registry and throws before SQL is built; `src/Query/ProductQuery.php` is the only builder of catalogue read SQL — one prepared page statement plus a `COUNT(*)` over the identical FROM and WHERE, tables only from `ProductQuery::TABLES` as `%i` identifiers, every value a prepare argument, taxonomy filters as EXISTS sub-queries only when present, and a `LIMIT` on every statement. Route arguments and schemas (T14): never write a read route's `args` or item schema by hand — take them from `Rest\RouteSchema` (`paging_args()`, `fields_arg()`, `query_args()`, `filter_args()`, `item_schema( $title, $extra )`) and implement `Rest\ReadController::get_item_schema()`, registering it as the route's `schema`; filter arguments are `{ operator, value }` objects named after the field, and `criteria_input()` turns validated parameters into `Criteria` input. A new filterable field also needs its SQL in `Criteria::FILTERS` and `ProductQuery` before its argument accepts anything. Hydration (T16, T17): `src/Query/Hydrator.php` hydrates a page of ids in a fixed query count — `_prime_post_caches()`, one `update_meta_cache()`, one `wp_get_object_terms()` across the catalogue taxonomies, one grouped variation count, one lookup-table price read, and two attachment primes for thumbnails with the `wc_placeholder_img_src()` fallback — and every column goes through `Field::read()` over `src/Query/Snapshot.php`, never a `WC_Product` (`woocommerce_product_read` must never fire on the read path; a test scans `src/Query/` and `ProductsController` for product construction and `get_price_html()`). A new registry field needs its getter on `Snapshot` (SnapshotTest fails otherwise). The rendered price is `Hydrator::render_price()` from lookup `min_price`/`max_price` with `wc_price()`/`wc_format_price_range()`. `src/Query/Catalogue.php` is the only way to read a page: it caches in object-cache group `bcm_catalogue` keyed on the criteria, fields, a sample formatted price and the posts' and terms' last-changed values. Tests count queries with `bcm_test_query_count()` over the recording read stubs in `tests/Support/read-stubs.php`. `GET /bcm/v1/products` returns real hydrated `items` (plus `parent_id` and `thumbnail_url`). Products and variations (T18, T20): a `category_ids` filter includes the chosen categories' descendants, expanded in `ProductQuery` through `get_term_children()` (never in `Criteria`, so views keep the chosen ids). `GET /bcm/v1/products/{id}/variations` (`VariationsController`, args from `RouteSchema::variation_args()`) reads through `Catalogue` with `Criteria`'s internal `parent` argument (never taken from a request: `Criteria::INTERNAL_ARGS`), in `menu_order` then id, 404 `bcm_not_found` for a non-product id; every list route answers through `ProductsController::response()`, and every row schema takes its extras from `RouteSchema::row_extras()`. Variation rows carry `parent_name` and `attribute_summary` ("Blue / Large") built in the Hydrator from attribute meta and one `get_terms()`, never `wc_get_formatted_variation()`. Seeded read tests run the real prepared SQL: `tests/Support/SqlEvaluator.php` evaluates the read path's SELECT dialect in memory (extend it, with a case in `SqlEvaluatorTest`, if a statement needs more; it throws on anything else), and `tests/Unit/Query/SeededCatalogue.php` seeds its tables and the hydration fixtures from one definition. Categories (T21): `GET /bcm/v1/categories` returns the nested `product_cat` tree with counts from one grouped statement in `src/Categories/Counts.php`, which reuses the grid's conditions only through `ProductQuery::conditions_sql()` (never by parsing a statement); the tree is cached in `bcm_category_tree_` transients whose version the term hooks renew, registered from `Plugin::hooks()` on `init`. Export (T22): `src/Export/CsvWriter.php` is the only CSV writer — later exports (preview sample, batch changes, audit list) go through it and a `RowSource`; `GET /bcm/v1/export` streams the grid's rows 100 at a time. Test stubs: define each function once across `tests/Support/*.php`, inside a `function_exists` guard; the object cache and last-changed stubs live in `read-stubs.php`. The wp-env seeded assertions for T18 and T20 (the same id sets on a real catalogue, the variations total against `get_children()`) are still to run. Counts and selections (T19): `total` comes through `src/Query/CountCache.php` — a 60-second `bcm_count_` transient keyed by a hash of `Criteria::conditions()`, the posts' and terms' last-changed values (persistent object cache only) and a version its hooks renew on product saves and product-taxonomy term changes; never count with `SQL_CALC_FOUND_ROWS`. `POST /bcm/v1/selection` (`Rest\SelectionController`, `Access::can_write`, args from `RouteSchema::selection_args()`) answers `{ count, token }` for a filter or an `ids` list; preview, batches and apply take the token and must resolve it only through `Selection\SelectionToken::parse()`, which returns a `Selection\Selection` (criteria rebuilt by `Criteria::from_conditions()`, or ids in order, deduplicated) or 403 `bcm_invalid_selection`; a selection above `Selection::MAX_OBJECTS` (100,000) is 400 `bcm_selection_too_large`. Operations (T24): every bulk action implements `Operations\Operation` (`describe()`, `validate()`, `compute()`, `apply()`), normally by extending `Operations\BaseOperation`, which resolves the accepted fields from the field registry by edit kind (never list field keys in an action) and validates arguments from one spec list that also produces the published schema; every action takes `field` and `skip_already` (default on). `compute()` returns an immutable `Operations\Result` (`changed`, `already`, `skipped`, `failed` with a plain reason); `apply()` writes only a change, through `Field::write()`, never saves, and throws `WriteRefused` when the field refuses. Resolve and validate actions only through `Operations\Registry` (`get()`, `validate_list()`, which refuses an empty list, more than twenty steps, unknown ids, unaccepted fields and invalid arguments with `bcm_` codes before any object is read, and returns normalised arguments — store and hash those). Each editable field declares its panel group (`Operations\Group`). `GET /bcm/v1/fields` answers `{ fields, actions, groups }`. A new action is added in `Registry::defaults()` and must keep every field edit kind resolving to an action. Actions (T25–T27): every action now has a real `compute()`; an action ending in "write this value" goes through `SetValue::outcome()`, numeric actions share the public static helpers on `Round`, and `Terms::apply()` writes the full list through `wp_set_object_terms()` then the field setter. Shared action helpers are protected statics on `BaseOperation` (`value_outcome()` for "write this value", `number_outcome()` and the decimal-text helpers for numeric actions); never make an action call another action's statics. Row validation (T28): every computed Result passes `Operations\Validator::check( $subject, $result, $args )` before apply() — build one per run with `Validator::for_request()` (current user) or `Validator::for_user( $fields, $batch_user_id )` (background) — which returns the list of Results to apply (a second one clears the sale price when a regular price change leaves it not below and `clear_invalid_sale` is on): permission first (`bcm_cannot_edit`, skipped), then the registry's validator through `Field::refusal( $subject, $value )`, the dry run `Field::write()` itself uses (never re-implement a field check elsewhere), then the cross-field rules (in-run SKU clash, sale not below regular). A Result's reason is a §4.8 sentence and may not contain a `bcm_` code; the code goes in its `code` field. Batches and the writer (T31, T32): `POST /bcm/v1/batches` creates a batch only through `Engine\BatchFactory` (replay check, `validate_list()`, selection materialised into pending items, `bcm_batch_created` fired; nothing enqueued); its two SQL reads should move into `src/Query` (follow-up). Every product write goes through `Engine\Writer` (`write()` for one object, `run()` around a chunk), which calls `Validator::check()` between compute() and apply(); pass the batch's user id as its third constructor argument in background work. `src/Engine/` must not write meta or SQL or call setters of its own (a test scans for it). Journal (T33, T29): background and one-item batches (inline, detail panel, term writes) write through `Writer::for_batch( $operations, Journal::from_settings( $fields ), $batch_id, $user_id )`; the writer itself calls `Engine\Journal` — `already_done()` before loading (a retried object is skipped with `bcm_already_done`), `modified_gmt()` after loading, `record()` after save — and never journal from a hook. One `bcm_changes` row per field a step named (applied, failed or skipped with its plain reason); an `already` Result writes nothing unless its step's `skip_already` is off and *Record unchanged rows* is on. A throwing `save()` becomes failed Results (`bcm_save_failed`) and does not stop the caller; a failing journal insert still throws. The wp-env checks for T29 and T33 (modified time untouched on an already-correct product; a killed and re-run write moving each price once) and T29's Jest test are still to run. Chunk runner (T34): `Engine\ChunkRunner` handles `bcm_run_chunk` (group `bcm`), first enqueued on `bcm_batch_created`; use only the public `as_*` functions and never reference WooCommerce's internal batch-processing classes or the queue runner's options (ChunkRunnerTest scans `src/Engine/`). A run works only a queued or running batch, claims with `BatchRepository::claim_chunk()` (one locking UPDATE with a 5-minute lease: `claim_token`, `claimed_gmt`), writes through one `Writer::for_batch()->run()` inside `wp_defer_term_counting()`, marks items with their plain `message`, adds the counters, and chains its successor or finalises through `BatchRepository::transition()` (conditional on the current status, so T35's cancel needs only to set `cancelled`). Engine status changes go through `transition()`, never `set_status()`. The adapted chunk size and its reason live in the batch's `chunk_size` and `note`.
