# Bulk Catalogue Manager security and correctness review (main at 4617521)

I found no blockers: no SQL injection, no way around a permission check, no unsafe unserialize, and no product saved on behalf of a user who may not edit it. The two major findings are both ways a price change can be applied twice when a background run is slow or gets killed. I confirmed each code path by reading it end to end. Findings marked **plausible** also depend on runtime conditions I could not test. Paths below are relative to the repository root.

## Major

**M1. A save followed by a killed request can repeat a percentage change on retry (plausible).** `src/Engine/Writer.php:220` saves the product, and `:231` writes the journal only after that. `Journal::already_done()` (`src/Engine/Journal.php:98`, `ChangeRepository::has_object()` at `:149`) looks only for journal rows. Slow save hooks are where timeouts usually happen, after WooCommerce has already written the product row. If the process dies there, the retry finds no journal row and applies "+10%" a second time. This is the exact case SPEC §12.3 promises to prevent.
*Fix:* before `save()`, write one intent row per field (for example `result='pending'`) holding the computed new value. After saving, change it to `applied`. On retry, when an intent row exists, don't recompute: write the recorded absolute new value, or skip if the product already holds it.

*Resolved* in 1f960c5: the writer records intent rows (`result = 'pending'`, the computed new value) just before `save()` and settles them to applied or failed after; a retry that finds intent rows writes the recorded absolute value, or leaves it where the product already holds it, and settles the rows (`Writer::replay()`). The undo planner treats an unsettled intent row as applied. SPEC §12.3 updated.

**M2. A run that takes over a stale claim can process the same items as the run that still holds them (plausible).** `BatchRepository::claim_chunk()` (`src/Data/BatchRepository.php:407`) lets any claim older than five minutes be taken over. The retry is scheduled six minutes ahead (`src/Engine/ChunkRunner.php:268`). The first runner's loop (`ChunkRunner.php:310-328`) never checks that it still owns each item. When a chunk runs longer than five minutes (heavy save hooks, or WP-CLI runners with no time limit, where `php_time_limit()` wrongly assumes 30s), both runners work through the same items. The `already_done` check before load does not close this race: both can pass it before either one writes its journal row.
*Fix:* just before each write, claim the item alone with `UPDATE … SET state='working' WHERE item_id=%d AND claim_token=%s AND state='pending'`, and skip the item if no row changes. Also stop claiming new items once elapsed time passes 80% of the lease.

*Resolved* in ca53a5e: each item is claimed on its own just before it is written (`UPDATE … SET state='working' WHERE item_id=%d AND claim_token=%s AND state='pending'`) and skipped when no row changes; a run claims no new item past 80 per cent of the lease and releases the rest; stale `working` items return to pending; `php_time_limit()` takes no limit as the lease. SPEC §12.4 updated.

## Minor

**m1. The client chooses the batch `source`.** See `src/Rest/BatchesController.php:88` and `:585-593`. `POST /batches` accepts `inline` and `tree`. `Progress::sweep()` (`src/Engine/Progress.php:355`) marks a *running* `inline` batch as failed after ten minutes without a claim. A background batch labelled `inline` is therefore killed whenever Action Scheduler falls behind, and `tree` mislabels product batches in the history.
*Fix:* allow only `['bulk']` on this route and set the source on the server.

*Resolved* in b3ec389: `POST /batches` accepts only `source: bulk` and always creates a bulk batch.

**m2. Raw exception text is returned in `data.details`.** See `src/Engine/InlineWrite.php:287` and `src/Categories/Writer.php:404`. Both catch any `\Throwable`, including exceptions thrown by third-party save hooks and database errors, and send the message to the client. That can expose SQL or file paths.
*Fix:* log with `wc_get_logger()` and leave `details` out. The fixed-text `RuntimeException` messages in `BatchFactory` are harmless, but drop them too for consistency.

*Resolved* in b3ec389: `Rest\Refusal::unexpected()` logs the throwable through `wc_get_logger()` (source `bulk-catalogue-manager-for-woocommerce`) and returns only the sentence; InlineWrite, Categories\Writer and BatchFactory's three not-recorded refusals use it.

**m3. Term actions never check `assign_terms`.** `src/Operations/Terms.php:247` calls `wp_set_object_terms()`, and the only check is `edit_post`. A custom role with `edit_products` but without `assign_product_terms` can recategorise products.
*Fix:* in `Validator::check()`, or in `Terms::compute()`, require `user_can( $user, get_taxonomy( $tax )->cap->assign_terms )`, against the batch user in background runs.

*Resolved* in 31c6714: `Validator::check()` skips a change to categories, tags or shipping class unless the user (the batch user in background runs) has the taxonomy's `assign_terms`.

**m4. Category writes check only `manage_product_terms`.** See `src/Rest/Access.php:128-137` and `src/Rest/CategoriesWriteController.php:90-112`. Core checks the per-term capabilities `edit_term` and `edit_product_terms`.
*Fix:* for PATCH and move, also require `current_user_can( 'edit_term', $id )`; for create, require the taxonomy's `edit_terms`.

*Resolved* in 31c6714: `Access::can_manage_terms()` also requires `edit_term` on the category a PATCH or move names (an unknown id stays 404) and the taxonomy's `edit_terms` for a create.

**m5. A variation edit can save a parent the user may not edit (plausible).** `Access::can_edit_object()` (`src/Rest/Access.php:161`, `:172`) checks `edit_post` on the variation itself, which depends on the variation's own author. `Writer` then runs `WC_Product_Variable::sync()` on the parent (`src/Engine/Writer.php:227-229`, `:256`), which saves the parent with no check. This matters only if a variation's author differs from its parent's.
*Fix:* for a variation, also require `edit_post` on `get_parent_id()`.

*Resolved* in 31c6714: a variation also needs `edit_post` on its parent, in requests, background runs and the undo planner.

**m6. The server enforces preview only for filter selections.** `$checked` at `src/Engine/BatchFactory.php:225` is false for an `ids` selection, so a bulk batch of ticked rows can be applied without ever calling `/preview`. The owner's rule is that every bulk write is previewed first.
*Fix:* require `preview_hash` for `ids` when the source is `bulk`. `Preview::hash()` already accepts id arrays (`src/Engine/Preview.php:217`).

*Resolved* in d21e258: a bulk batch of an `ids` list or id token needs its preview's `preview_hash` (409 `bcm_preview_stale` otherwise); the probe checks it live. SPEC §9.1 updated.

**m7. The undo planner checks the wrong user's rights.** `src/Undo/Planner.php:395` checks the *original* batch user. The write itself (`ChunkRunner` through `Validator::for_user`) correctly checks the person undoing. If the original author is deleted or demoted, the batch can never be undone.
*Fix:* pass the current user into `plan()` and check against them.

*Resolved* in 31c6714: `Undo\Planner::plan()` takes the person undoing (the current user by default; the undo route passes it).

**m8. Background runs always apply kses, whoever queued the batch.** `src/Fields/Field.php:398` and `src/Categories/Writer.php:610` call `current_user_can( 'unfiltered_html' )`. Background runs have no current user, so an administrator's find-and-replace or undo on descriptions silently strips allowed HTML, and an undo does not restore the exact old value. This is safe but wrong.
*Fix:* take the batch user from the `Validator` context and use `user_can( $user_id, 'unfiltered_html' )`.

*Resolved* in 31c6714: `Field::acting_as()` makes the kses decision `user_can( $batch_user, 'unfiltered_html' )` in background writes; category writes use the user their batch is recorded for.

**m9. An unknown argument name is echoed into the error message.** See `src/Operations/BaseOperation.php:161-163`. It is safe only because the UI renders text as text.
*Fix:* wrap it in `sanitize_key()` and cap its length.

*Resolved* in b3ec389: the name goes through `sanitize_key()` and is cut to 40 characters.

**m10. `GROUP_CONCAT` can truncate category ids.** `src/Categories/Counts.php:79` builds the grouped term list under MySQL's default 1024-byte limit and never checks for truncation, so a product in very many categories gets wrong counts, as does any result past `MAX_GROUPS`.
*Fix:* count with `COUNT(*) … GROUP BY term_id` over the same conditions.

*Resolved* in b6e9830: counts are `COUNT(DISTINCT …) … GROUP BY` per ancestor over the tree's (category, ancestor) pairs; no `GROUP_CONCAT`, and the seeded expectations hold.

## WordPress.org Plugin Check and human reviewer

**p1. `DROP TABLE` uses string interpolation.** See `src/Data/Cleanup.php:102`. The code comment says identifiers "cannot be passed through prepare()". That is false since WordPress 6.2, and the plugin uses `%i` everywhere else.
*Fix:* `$wpdb->query( $wpdb->prepare( 'DROP TABLE IF EXISTS %i', $table ) )`.

*Resolved* in 8f68730: `$wpdb->query( $wpdb->prepare( 'DROP TABLE IF EXISTS %i', $table ) )`.

**p2. `base64_encode` and `base64_decode` in `src/Selection/SelectionToken.php:169` and `:179`.** Plugin Check raises its base64 "obfuscation" warning here, and human reviewers routinely ask about it. Tokens can also reach 4 MB of request body.
*Fix:* keep the payload on the server in a `bcm_selection_` transient under a random id, and make the token that id plus a hex HMAC. Register the new prefix in `Data\Registry`.

*Resolved* in f6db5d4: the selection is kept in a `bcm_selection_` transient (registered in `Data\Registry`) under a random id; the token is the id and a hex HMAC; no base64 remains.

**p3. The 3-letter prefix (plausible reviewer flag).** Reviewers commonly ask for prefixes of four or more characters (`BCM_FILE`, `bcm_*`). There is also a concrete collision risk: `src/Data/Cleanup.php:74` cancels **every** action in the Action Scheduler group `bcm` on uninstall, which would include another plugin's actions if it uses that group name.
*Fix:* at minimum, rename the Action Scheduler group to the full slug.

*Resolved* in 2fd2b83: the Action Scheduler group is the full slug `bulk-catalogue-manager-for-woocommerce` (Registry constant, Cleanup, ChunkRunner, Pruner, tests, probe, SPEC §15). The `bcm_` option and hook prefix is unchanged. (2026-09-24: the prefix itself is now `bulkcat_` / `BULKCAT_` / `bulkcat-` and the REST namespace `bulkcat/v1`; the names above are as they were when this review was written.)

**p4. Uninstall ignores multisite.** `Cleanup::uninstall()` cleans only the current site.
*Fix:* when `is_multisite()`, loop over `get_sites()` with `switch_to_blog()`.

*Resolved* in 8f68730: `uninstall.php` runs the cleanup through `Cleanup::on_every_site()`, which switches to each site of a network.

## Checked with no issue found

- **SQL:** every statement goes through `prepare()` with `%i` identifiers taken from constant allow-lists. Sort columns and filter columns are literal `switch` cases or `SORT_COLUMNS` lookups, and every statement has a `LIMIT`.
- **Stored operations:** `Writer::resolve()` accepts only action ids from `Operations\Registry`, and nothing turns a class name into an object. `ValueCodec` only JSON-decodes into arrays, and there is no `unserialize`, `eval` or external call anywhere.
- **Action Scheduler:** handlers take only an integer batch id, and a run is limited by the batch's recorded user.
- **Race conditions:** undo, cancel and finish transitions use compare-and-set (`transition()`), and a second undo of the same batch loses cleanly.
- **Cross-site request forgery:** core's cookie-plus-nonce check covers every route, including the GET export.
- **Mass assignment:** `PATCH` intersects its input with `editable()`, and `validate_list()` rejects unknown keys at both the step and argument level.
- **CSV injection:** the formula guard covers the header row too, and the leading-space trim is correct.
- **Find and replace:** `preg_quote()` plus a replacement callback, so no input can become a regex or backreference.

## Five controls to keep

1. **`Rest\Routes::add()` refuses unguarded routes.** It refuses any endpoint whose permission callback is missing, not callable or `__return_true`, and every check lives in `Rest\Access`.
2. **Selection tokens are sound.** The HMAC-SHA256 includes a context string, the comparison uses `hash_equals()` against the computed value, and each token is bound to a user and an expiry. Filters are re-validated through `Criteria::from_conditions()` when the token is read.
3. **The per-object permission check comes first, in both contexts.** `Validator::check()` runs it before anything else: `current_user_can` during a request, `user_can( $batch_user )` in background runs. Refused objects are reported as skipped, never silently dropped.
4. **One query builder.** `ProductQuery` is the only place catalogue SQL is built, with `%i` identifiers from `TABLES`, every value passed as an argument, and `conditions_sql()` reused rather than re-parsed. The repositories follow the same discipline.
5. **Stored operations cannot run arbitrary code.** They resolve only through the `Operations\Registry` allow-list, `BaseOperation::validate()` rejects unknown arguments, and every value is written through `Field::write()`, which re-runs `clean()` and `refusal()`, so preview and write enforce the same rules.
