## 1. Purpose

A shop owner with thousands of products needs to change many at once. WooCommerce offers a twenty-row list and a bulk edit form covering a handful of fields, on the current page only, with no preview and no way back. This plugin adds one screen under **Products** where the whole catalogue can be filtered and edited in bulk, safely. Three promises shape every decision.

**1.1 Simple first.** The user is a shop owner, not a developer. Every control says what it does in ordinary words, and no raw database key is shown. Where simplicity and completeness conflict, simplicity wins and completeness goes to version 2.

**1.2 Native only.** The plugin edits native WooCommerce product data through WooCommerce's own CRUD classes, on a bare WordPress and WooCommerce install with nothing else present and no site-specific code.

**1.3 Reversible.** Products have no revisions in WooCommerce, so undo is ours to build. Nothing is written until a preview has shown what will change, every change is recorded with its previous value, and every batch can be reversed.

Free under GPL-3.0-or-later, built to WordPress.org directory standards from the first commit.

## 2. Non-goals

- **Per-customer or per-group product access.** Not a WooCommerce concept, and never built into this plugin. A separately installed plugin may add actions for values it owns through the external action contract (§6.1, [EXTENSIONS.md](EXTENSIONS.md)). This plugin then previews, journals and reverses those changes, but holds none of their logic.
- **Creating or deleting products.** Version 1 edits products that already exist.
- **Importing.** WooCommerce's native CSV importer stays the import path.
- **A spreadsheet.** No formula bar, no fill handle, no free-form cell paste.
- **Orders, customers and coupons**, **front-end output**, and **editing data belonging to other plugins**, except through that plugin's own registered provider (§6.1).
- **Paid tiers, upsells, telemetry or any external service.**

## 3. Definitions

- **View** — the current filters, search, sort, columns, layout and page size.
- **Selection** — an exact server-held set of product/variation identities. Ticking rows or selecting every match captures identities, independently of later changes to the view or catalogue. Composition adds/removes identities without re-running earlier filters.
- **Batch** — a selection plus an ordered list of operations, applied in the background and recorded as a unit. It is the unit of preview, progress, history and undo, and the interface calls it a **change**.
- **Chunk** — a slice of a batch processed by one scheduled action. Never appears in the interface.
- **Journal** — every touched field's before and after value, written inside the same code path that saves the product. Undo reads it. Never appears in the interface.
- **Audit log** — the readable view over the journal: who, when, which product, which field, from what, to what.

## 4. Screens

One admin page, **Products → Bulk Catalogue Manager**, registered with `add_submenu_page()` and rendered as a single React application from `@wordpress/components` and `@wordpress/dataviews`, bundled through `wp-scripts`, with client-side routing between the panels below and a Settings tab holding §11. No WooCommerce admin JavaScript framework is loaded; the page inherits the admin's own look and colour schemes.

### 4.1 Catalogue

**Layout.** A resizable, collapsible category panel on the left, its width and state remembered per user; the DataViews table fills the rest; a sticky selection bar appears when anything is selected. Below 960 pixels the panel becomes a button opening it as a sheet.

**Controls.** Search on name and SKU. Filters for category, tag, type, status, catalogue visibility, featured, stock status, whether stock is managed, price and stock ranges, tax class, shipping class and last modified, shown as chips reading as sentences such as "Stock is 0 or less". New Status controls use native status names. Existing saved **Off** and **Changed outside this screen** predicates remain exact and are labelled as legacy status filters (§5.5); loading one never broadens it to all Draft products. A category filter includes every category below the chosen ones, as choosing a branch in the category panel does. Multi-column sort, column chooser, density, export (§10). Page size 25, 50 or 100, default 25. A table or grid layout, table being the default and the layout the design targets. A mode switch between **Products**, **Products and variations** and **Variations only**.

**Columns.** By default thumbnail, name linking to the classic product editor, SKU, status badge, regular and sale price, stock status with quantity, and categories; which columns appear is the owner's choice. The status badge shows the native stored status and is edited in place. **Scheduled** is the effective `future` state, not an ordinary writable choice; an old remembered record does not rename a new Status control. There is no separate Available column. The **Shown in shop and search** switch (§5.3) is a listing control the owner may add; it is not a default column. Each row also carries a checkbox and a menu with *Edit details*, *Open product editor*, *View product (new tab)*, *Duplicate* and *Move to Trash*, subject to current native permissions and availability. An inline cell opens on click or Enter, commits on Enter or blur, reverts on Escape.

**Native row actions (ticket21).** Editor and View use native destinations; View opens an isolated tab. Duplicate and Trash use the original WooCommerce/WordPress handlers, nonces, hooks, redirects and errors, with fresh native permission checks at execution. Variable-product children follow native behavior. Variations expose Edit details and an explanation instead of parent-native destinations. Trash is unavailable when native Trash is disabled; this menu never permanently deletes a product. A published product with sales keeps the native sales warning, and Cancel makes no change. These actions do not create plugin History entries or plugin Undo; recovery from Trash uses the native Undo link or Products → Trash. Exact selection is preserved when leaving and returning, a duplicate is not automatically selected, and unavailable selected objects remain honestly omitted from export. A failed return refresh preserves selection and offers a read-only retry.

**Detail panel.** A `DataForm` drawer holding every version 1 field for one product, including the four-way catalogue visibility field and the full status field, so the row stays simple. Saving uses the same engine as a bulk action, journalled and undoable, as a batch of one.

**Individual save and readback.** An ordinary inline, switch or detail edit writes once through the synchronous single-product route. Repeated events for the same pending intent share that write; incompatible edits of that object wait for its outcome. A confirmed result reconciles the current filtered page, counts and pagination without altering exact selection. Superseded reads cannot restore an old query or overwrite a newer draft. Completion offers the returned change in History, where supported Undo remains available. A failed refresh is explicitly separate from a completed save; **Refresh results** only reads.

A partial answer reconciles the actual row and remains a partial outcome with its History entry. A committed validation or permission refusal fence leaves corrected input editable. Each ordinary Save reserves its object before grant issuance and verifies safe identity persistence before its single synchronous PATCH. The tab stores only `{object_id, grant:{uuid,request_proof,accept_until,operation,intent}}` in a site/user-scoped session store; values, drafts and deduplication keys stay in memory. Strict storage is additive to best-effort selection storage. Updates reread and merge the store so standalone editing owners cannot remove another object’s held grant. Failed persistence prevents PATCH; failed verified removal keeps the object held even when its outcome is known.

An uncertain response triggers one immediate payload-free receipt read and, if still unresolved or unavailable, one further read after one second. Reload locks restored objects synchronously and makes one read-only pass. **Check save outcome** and History remain available; no automatic or explicit mutation resend is offered. Inline PATCH and resolution opt out per request from both the plugin’s and api-fetch’s nonce retry path; ordinary callers keep their nonce recovery. A missing, expired, denied, conflicted, pruned or malformed observation cannot release the identity or issue a replacement. A closed receipt or committed refusal is adopted automatically and released only after storage removal verifies. Resolution contains no row/results: a strict current-row read and current-query reconciliation follow separately. A failed read preserves the known outcome and newer drawer text, and never substitutes an older row; current values after Undo are not attributed to the earlier Save. Unclosed inline History suppresses queue advice and Undo, including unfinished legacy inline rows. The bounded native concurrency/browser qualification is recorded below; target-host release qualification remains separate.

**Native single-save receipt transport (1 October 2026).** One Save remains synchronous. `POST /requests` with `operation: 'product.inline'` and `intent: {object_id, source, values, keep_changed_status?}` returns the existing UUID/proof/deadline plus an opaque canonical intent. Send those `uuid`, `request_proof`, `intent` fields with the original native value fields on `PATCH /products/{id}`. A legacy PATCH without a grant gets 409 `bulkcat_invalid_request` with reload guidance. Internal `InlineWrite::write()` and historical native/bulk/Undo APIs keep their existing meaning. `source` is `inline` or legacy single-item `bulk`; neither makes this transport queueable. The optional `fields` response projection is not mutation identity.

Payload v1 is pure: a positive integer object ID, one of those sources, a nonempty map of native field identifiers to bounded JSON values, and an explicit boolean `keep_changed_status` (default false). It preserves scalar types and array/list order, sorts map keys bytewise (`SORT_STRING`), bounds nesting at 16 and JSON bytes at 65,536, and invokes no field/action normalizer or product read. Its root key order is `object_id`, `source`, `values`, `keep_changed_status`. Canonical bytes use PHP `json_encode` with `JSON_THROW_ON_ERROR | JSON_PRESERVE_ZERO_FRACTION | JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE`; invalid UTF-8 and unsupported values are refused, never repaired. The keyed commitment binds the JSON array `['bulkcat/inline/1', payload_version, registry_revision, site-as-string, installation-epoch, owner-as-int, normalized-payload]` with HMAC-SHA256 under the auth salt, before any live cleaning or redaction. No values or value-derived plaintext keys enter grants, receipt metadata, URLs or logs.

The canonical envelope is exactly `{version:1, payload_version:1, registry_revision:64-hex, object_id:int, source:string, commitment:64-hex}`. The registry revision is SHA256 of these exact version-controlled UTF-8 bytes, including a final LF, with no CR characters:

```text
bulkcat/native-inline-write/1
payload=1;actions=native-single-object-v1;status=set_status;variations=off;keep=false
```

This describes supported native interpretation, never product values, time, translated labels or serialized callbacks. `InlineReceiptTest` pins the bytes. A semantic change must bump the descriptor/version and preserve opaque envelope parsing. Unsupported signed payload versions or registry revisions refuse actual resends (`bulkcat_inline_version`, 409); payload-free `POST /requests/resolve` still verifies the original signed envelope without requiring its old normalizer to execute.

Dispatch is ordered: parse and authenticate the envelope for operation, current owner/site/epoch and object/source; check current screen/object/variation-parent disclosure rights; independently normalize a PATCH under its signed payload version and compare its commitment with `hash_equals`; read the existing receipt before expiry/live preparation. A changed or invalid payload gets 409 without fencing or modifying the receipt. Resolution returns `{receipt_state, batch_id?, write_status?, steps?, replayed}`; state is `not_accepted`, `refused`, `unclosed` or `closed`. Closed status is the original `complete|partial|failed`; steps contain only public native field identifiers, enum states and allowlisted codes. They contain no values, row, operations, reason or context. Immediate confirmed PATCH additionally retains `{item, batch_id, status, results}`. Duplicate PATCH and resolve return the safe receipt alone. Fetch the current row separately; it is not evidence of what the historical request wrote.

Only a PATCH without a visible receipt claims the existing unique owner/UUID key in a foundation transaction. After waiting, it rereads the winner before preparation. A surviving batch with that UUID but no receipt is refused through `BatchFactory::earlier()` without replacement or a no-effect fence. A genuinely new claim checks deadline/execution rights and calls live `InlineWrite::prepare()`, preserving native field validation/cleaning, dry-run, publication permissions, parent/variation scope and journal semantics. A confirmed pre-effect validation/permission refusal commits a bounded tombstone (`state=refused`, `result_kind=inline_refusal`, `result_id=validation|permission`, retained through issuance + eight days) with no batch. Its immediate error includes `receipt_state: refused`; subsequent replay/resolve returns a safe refused receipt. Permission denials that prevent disclosure are not tombstones.

Successful acceptance atomically records the receipt, header and exactly one item, adding `selection.inline_receipt = {version:1, object_id}`. It rechecks the deadline immediately before COMMIT, with no product effects, scheduling or batch-created event in that transaction. Only the original invocation receiving a confirmed new acceptance may run Writer once. No execution rights can be recovered from a later read, including after an ambiguous COMMIT. Before Writer, the receipt/header ownership, prepared operations, exact object/kind and first item claim must be positively confirmed. Native journal inserts/settlements on this path require exact affected-row acknowledgements. After a definite returned native outcome, item/counters/status and immutable `{write_status, steps}` closure commit atomically and strictly. Exceptions, caught save failures, unknown journal bookkeeping and failed closure remain unclosed. A lost closure COMMIT answer is resolved by reading the closure if it actually committed. Later supported Undo can change the batch status but cannot change its receipt closure.

Marked inline batches never enter chunk scheduling/recovery, irrespective of display source. Unclosed marked batches and legacy unfinished `source=inline` batches cannot be cancelled or undone, and History reads never sweep them to failed or infer completion from counts/values. History exposes safe `inline_receipt` to its owner with current object/parent disclosure rights and describes unclosed work as uncertain instead of stalled background work. Ordinary bulk recovery and closed-batch Undo retain their existing paths. Publication password editing is not exposed by the current registry: unknown, external and internal value fields are refused before acceptance; existing native private-status transitions retain their protected journal behavior. Future password editing must supply protected operation persistence before this contract is extended.

`not_accepted`, expiry, a missing/pruned row and invalid/foreign proofs do **not** establish a terminal no-effect fence. An original acceptance may be invisible after its final deadline check and still commit. Retain the held client identity and uncertainty; do not issue a replacement automatically. Only the same grant within its window and supported semantics may be explicitly resent, never automatically. This is at most one invocation per accepted grant, with read-only recovery of recorded outcomes; process death has no automatic resume, takeover, force-cancel or fabricated completion. Release of exceptional uncertainty requires separately authorized reconciliation/fencing after confirmed termination.

**Selection.** A header checkbox selects the page, then one line appears above the table: "All 25 on this page are selected. Select all 1,284 products matching these filters."

Both choices add exact identities to the existing selection. Search, filters, sorting, paging and mode changes retain it; **Review selected products** shows/removes off-page members. Deliberate **Clear search** clears search and selection, and says so in its name and tooltip ("Clear search and selection (N)"); its notice offers **Restore selection** while the released selection is still kept; **Clear selection** clears only selection. Transient empty text while replacing a search is not an explicit clear. Checkboxes reflect actual page membership; unticking one row after selecting all matches removes only that row. An open tab returning after the 15-minute authorization lease reauthorizes the same retained identities and previews again; membership is retained for seven days of inactivity, independently of the lease. Released intermediate sets become eligible for cleanup after one hour. Explain genuinely pruned work without silently re-running a former filter. See [the selection contract](EXACT-SELECTION.md).

**States.**

- *Loading* — skeleton rows at real row height, so the page does not jump.
- *Empty, no products* — "There are no products yet." with a link to Products → Add New, and nothing else on screen.
- *Empty, filtered* — "No products match these filters." with **Clear filters** and a list of the active filters, so the owner can see what excluded everything.
- *Error* — a notice saying what failed with **Try again**; the previous rows stay visible behind it rather than being cleared.
- *Change in progress* — a banner with the operation, a progress bar, a live count, cancel and a link to History; affected rows are pending and read-only.

### 4.2 Variations in the grid

In **Products and variations** mode a variable row carries a disclosure control and a count. Expanding fetches its variations in one request and inserts them as indented child rows sharing the parent's columns, each independently editable and selectable, with the attribute summary such as "Blue / Large" in the name column. Expansion is announced to assistive technology and is not persisted.

In **Variations only** mode the grid lists variation rows, each showing its parent name. Filters that suit a variation apply directly; category, tag, featured and visibility filter by the parent. This is the mode for "every variation that is out of stock". Expanding a product with no variations shows "This product has no variations yet."

### 4.3 Bulk action panel

A slide-over on the right, never a modal that hides the rows it is about to change, in four steps on one scrollable form.

1. **Scope.** The total exact selection, such as "24 selected products", with product/variation counts and review access. It may include rows outside the current view. A combined selection is never labelled as all matches of the current filter.
2. **Action.** Grouped as Pricing, Stock, Organisation, Shipping and tax, and Publishing. Choosing one reveals only its controls plus a plain description such as "Takes the regular price of each product and reduces it by the percentage you give." **Also apply to variations** appears where the field supports it — a field a variation has a value of its own for (§5.2 last column: per variation, or conditional such as status and stock quantity) — starting where the shop's setting for the field's group puts it (§11), with **Skip rows where the value is already correct**, on by default. The panel sends it as the step's `apply_to_variations` argument; left out, the server takes the same default; on for a parent-only or derived field, the step is refused with a plain sentence.
3. **Preview.** **Preview changes** produces §4.4. Nothing is written yet.
4. **Apply.** Enabled only after a preview that is still current.

**States.** Idle, configuring, previewing, preview ready, preview empty which disables Apply, blocked by validation with the reason in place, stale where the selection or settings changed so Apply becomes **Preview again**, applying, done. A disabled action carries a one-line reason.

**After apply.** The panel closes and progress moves into the selection bar: "Updating 1,284 products — 312 done." The owner may leave the screen; work continues on the server. On completion: "1,284 products updated. **Undo this change** · **View in History**".

Only actual full success clears submitted selection. Queuing/polling is not success. Failed, partial or cancelled work retains recoverable scope and an honest outcome. If the operator builds another selection while work runs, clear submitted identities while preserving later explicit additions, as specified in [the completion contract](EXACT-SELECTION.md#preview-apply-and-completion).

### 4.4 Preview

In this order.

1. A plain summary: "This will change the regular price on 1,284 products and 3,915 variations."
2. Counts: will change, already at the target value, cannot change with the reason for each.
3. A sample table — product, field, current value, new value — old struck through, new in bold, with a note on rows that will be skipped.
4. A warning block: a sale price above its regular price, a price falling to zero or below, stock going negative, a SKU duplicating another product's, and turning off Manage stock where WooCommerce will clear a stock quantity, backorders or low stock threshold (undo puts them back).

**Controls.** Sample size 25, 100, or every row up to 1,000. Filter to changed rows only. Download the preview as CSV before applying.

**States.** Computing; ready; nothing to do; partially computable, listing the products that could not be read and excluding them.

### 4.5 Confirmation policy

Ordinary individual edits use one Save/Update (inline edits commit on Enter or blur). Bulk changes use Preview → Apply. Native Status warnings stay in Preview: below the configured threshold (default 200 rows), Apply is one click; at or above it, one additional confirmation restates the count. A Status change that takes products off the site (Draft or Pending Review) always asks, naming what it will do, as the setting's help says (hotfix 1.3.1, FRONTEND-4). Optional-provider review safeguards remain. The existing confirmation behavior for other native actions is unchanged in this Status slice; general confirmation polish belongs to ticket20. Nothing requires typing a word to confirm.

Status Preview names the requested and effective native states, including a stored date that will keep Published scheduled. A successfully projected native password clear carries a redacted per-row boolean and warning count, counted across computed objects independently of the displayed sample (estimated with the existing totals when computation is capped); empty passwords, refused/no-op steps and failed projections never claim a clear. No password or password hash is exposed. The bulk panel, inline editor and detail drawer use the same server result. New edits never offer restoration or **Keep current status** on the basis of an old record. Historical Off/On outcome text remains readable for accepted legacy work. Wider publication Visibility controls and confirmation UX are separate follow-ups.

### 4.6 History and audit log

Batches newest first: when, who, what, how many rows, outcome, and whether it is still reversible, filtered by date range, user, action type and status. Expanding one shows its changes — object, field, old value, new value, result — paginated and searchable; there is no second tab for that detail. **Undo this change** runs through the preview screen first. A batch's changes export as CSV. A separate **Audit log** tab lists field changes across all batches, filtered by product, field, user and date range.

**Categories in plain words** (ticket 133 bug 3). History never shows a category id or a stored form: a category row is named by its path ("Clothing › Shirts › Golf") under a first column headed Category (Product or category when a batch holds both), parents and the default category by path ("Top level" for none), images by title, display types by WooCommerce's labels, a product's category list by names, and every name with its HTML entities decoded. The changes feed and the audit log carry these as `old_text` and `new_text` beside the stored values (the CSV exports keep the stored values); a category deleted since reads by the path its delete journalled. Each batch report carries a `headline` for a category change ("Renamed category Golf to Golf shirts", "Moved category Golf shirts to Clothing › Golf", "Reordered category …", "Made … the default category", "Deleted category …", "Merged category … into …") and for a product change whose steps only add, remove or replace categories ("Moved 15 products from Saucepans to Kitchen › Pots"); category writes record the id and the values before in their step so the headline can name both.

**States.** Reversible; partially reversible, with the conflict count; in progress, showing a progress row instead of Undo; completed with errors, expanding to the failing rows and reasons; not reversible, with the reason — outside the retention window, already undone, pruned, or a deleted or merged category (`permanent`). An undo batch is listed as "Undo of #418" and can itself be undone, offered as **Redo**.

### 4.7 Category manager

The tree at full width, with counts and a details pane. Create, rename, edit slug and description, change parent, reorder within a parent. Drag to re-parent and reorder, with an equivalent **Move to…** dialog on every node's menu for keyboard and screen reader users. Dropping a product selection onto a node adds that category to every selected product as an ordinary previewed batch.

**Delete… and Merge into…** (ticket 24, owner's ruling of 5 October). Delete… removes one category, or every chosen category when its menu is opened on one of several chosen, through `wp_delete_term()`, so the consequences are WooCommerce's own: subcategories move up to the deleted category's parent, the category comes off every product, and a product left with no category is put in the default category (WooCommerce's `force_default_term`). Merge into… first moves every product of the chosen categories into a target through WooCommerce's CRUD, as a bulk change does (at most 500 products; a bulk change moves more), then deletes them the same way. Both need `manage_product_terms` and `delete_term` on each category; the default category offers neither and is refused, as WooCommerce refuses it. A confirmation lists the categories by path and states the counts — subcategories that move up, products affected, products that will fall back to the default (named) or move into the target — and says plainly that a deleted category cannot be brought back, so this cannot be undone; its token (`POST /categories/delete` or `/categories/merge` with `preview: true`) is required to run it, and anything counted that changed since is refused 409 `bulkcat_preview_stale`. Each run is one `tree` batch (`delete_categories` or `merge_categories`, with the paths for History) journalling `term_deleted` (the path, as text), `term_parent` for each subcategory moved up and `category_ids` for each product whose categories changed, before and after as read from WordPress. **It is not undoable:** recreating a category gives it a new id, which menus, links, other plugins' settings and earlier History rows would not follow, so undo could not be exact; History lists these batches as not reversible with the reason `permanent`.

**States.** Empty — "You have no product categories yet." with **Create your first category**. Dragging — a drop indicator and a preview of the new path. Blocked — "A category cannot be moved inside itself." Read-only without `manage_product_terms`.

**Creation receipt and readback.** A confirmed creation needs a positive integer ID; retain its returned name (or the trimmed submitted name) and description, then refresh the tree without inserting a node locally. The shared tree owner exposes `recordCreated(item, submittedName)`, `dismissCreation()` and `creation` (`null` or `{ revision, id, name, phase }`), retaining `reload(): void`. Its phases are `refreshing`, `visible`, `missing` and `refresh_failed`: only the newest applicable read reconciles against the full returned tree index, including descendants hidden by panel search or collapsed branches. Reloads, query changes and newer receipts invalidate older requests before they can settle; failed reads retain existing nodes, and completions after unmount do nothing. A read-only retry confirms visibility only when that ID is returned. Dismissal hides the receipt without changing membership or allowing a pending completion to restore it. An incomplete save response is separate from confirmed creation: show "The server returned an incomplete save response. Check the category list before creating it again." and offer only refresh, never an automatic create retry. Ordinary individual Save/Update remains one action; bulk Preview → Apply and the configured count threshold are unchanged.

**Visible creation feedback.** The panel keeps one initially empty polite, atomic status outside the edit dialog. Its DOM container remains mounted across confirmed and incomplete outcomes, readback updates, dismissal and subsequent creation while the panel is open. This visible region is the sole creation announcement source; the nested native Notice speaker is disabled. It names the created category while refreshing, confirms it when the authoritative list returns its ID, and distinguishes an omitted category from a failed list request. Omission explicitly says there is no need to create it again. **Refresh category list** only reads; repeated failures keep the receipt and existing nodes. It never repairs membership or promises that an affected installation's category restriction has been fixed. Search, parent choices, category controls and the product selection are preserved. Save, Cancel, Close and Escape return focus to the opener; if first-category readback removes the focused empty-state opener, focus moves to the local status. A successful retry similarly transfers focus when its button disappears. Background completion leaves focus alone if the user has moved elsewhere. Incomplete POST responses remain unconfirmed warnings, not success receipts.

### 4.8 Error wording

Errors name the thing, say what happened and say what to do, in one or two short sentences, with no codes in the main text; a technical line sits behind a **Show details** toggle. Category error notices retain the native error border, underlined disclosure and focus indicator while keeping disclosure text contrast readable in normal, hover and keyboard-focus states. Examples:

- "We could not save 3 products because another user was editing them. Try again in a moment."
- "Stock quantity has to be a whole number. Enter a number like 12."
- "A product with the SKU SHOE-42 already exists, so this SKU was not applied to 2 products."

## 5. Fields

### 5.1 The field registry

Version 1 edits single-value native fields. Each is declared once in a PHP registry supplying its type, storage, sanitiser, validator, REST schema fragment and DataViews definition. Route `args`, with their `validate_callback` and `sanitize_callback`, are generated from it, so grid, REST, preview and writer cannot disagree. The client reads it through `GET /fields` and hard-codes no field list.

### 5.2 Field table

### 5.3 Listing controls: "Shown in shop and search"

Listing controls change listing only; a hidden product can still be opened by link and bought. Set Status to Draft to take a product off sale (§5.5).

Catalogue visibility has four values, three more than most owners want. The **Shown in shop and search** switch (called Visible on site before 29 September; its key `visible_on_site`, saved views, journal rows and CSV column id are unchanged) is one switch over the same storage: on (**Shown**) means shop and search, off (**Hidden**) means hidden from both. A product in one of the two middle states renders in a third, neutral position labelled **Partly**, with a tooltip naming the exact state, and clicking it offers the two real choices. Nothing flattens a middle state into a full state without the owner choosing it. It is a secondary listing control, not a default column; the four-choice **Catalogue visibility** field stays in the detail drawer. The selection bar's quick actions read **Show in shop and search** and **Hide from shop and search**. The CSV heading is the label, so it reads "Shown in shop and search"; a view that does not show the column exports without it.

Visibility and `post_status` are separate fields, so a grey **Draft** or **Pending** badge sits beside the switch where the status would keep the product off the site anyway. The interface never tells an owner a draft is visible. Listing controls remain independent of publication status. Status edits preserve them; legacy-record cleanup follows §5.5.

### 5.4 Value rules

Prices are stored through `wc_format_decimal()` at the shop's precision. Empty is a real value distinct from zero: clearing a sale price writes an empty string, as WooCommerce expects. A sale price not below its regular price fails validation and is reported in the preview; the row is skipped rather than cleared, and the form offers "clear the sale price where it is not below the regular price" as an explicit choice. An inline or detail-panel save of both prices lets the new regular price clear an old sale price that would no longer be below it, but a sale price typed at or above the regular price is refused, never written as a clear. A result below zero is refused and the row reported as skipped, never clamped. A stock status change where stock is managed (its own, or for a variation its parent's) is skipped with its reason, since WooCommerce sets the stock status from the quantity on save; preview and result count only what is stored. A name changed by find and replace does not change the slug.

### 5.5 Native Status and legacy compatibility

New Status edits request exactly Draft (`draft`), Pending Review (`pending`), Private (`private`) or Published (`publish`). Private → Draft → Published and Pending → Draft → Published end Published when the stored date permits it, regardless of any remembered record. An ordinary control never writes literal `future`. WordPress may store `future` when Published has a GMT date at least 60 seconds ahead, and stores `publish` below that boundary. Preview predicts the effective state using the same stored date and an injected clock; save readback remains authoritative. A floating Draft/Pending with zero stored GMT and no explicit date edit is different: native `wp_update_post` resets its date to save time, even when the apparent local date is future. Preserve this evidence when qualifying prediction inputs; the observed CRUD date is null in that case. Bind the stable stored local/GMT inputs and floating-date mode, never a derived ticking save time.

A recorded publisher’s Status-only Pending save preserves its existing explicit slug through an exact-object native save filter, removed in finally; it never changes the current user or adds a second save. The same temporary exact-object lifecycle boundary corrects only unchanged password slashing transport, preserving raw canonical object/journal values, native Private clearing and intentional changes by other hooks. Child and parent edit permissions remain separate from publication permission.

Variation Enabled permissions remain distinct from product publication permission, but variations follow the same native Publish/Future date boundary. Recovery recognises a stored Scheduled outcome of an earlier Publish intent from a different status preimage independently of the resumed clock. A still-unwritten Future→Publish intent is not treated as that landed transition; it remains subject to the normal resave checks and one native save.

The native variation datastore omits publication-password loading and updating. The internal protected reader therefore inspects the actual stored variation password through the native post API. Until a supported restoration path is qualified, a variation with a stored password cannot be changed to Private, and an internal variation password restoration is refused before setters/save, including replay and forced Undo. Ordinary password-empty variation status edits remain supported. This refusal preserves the uncommon native preimage instead of promising an Undo that the datastore cannot perform; no public password writer or broader variation-property adapter is added.

Native publication effects are part of the change. In particular, the WordPress save path clears a password when it stores Private. Unrelated prices, categories, tags, listing settings, stock, other metadata, slug, menu order and variations are preserved. Dates and scheduling events follow the actual native save context. The pinned WooCommerce product API, native editor permissions and save side effects are distinct evidence: a CRUD setter alone is not proof of permission enforcement, scheduling or password readback.

`tests/fixtures/native-status.json` is the comparison table. `tests/probe/native-status.py` submits real native product-editor/variation forms and manager requests on paired UUID-owned synthetic objects; it records capabilities, status/date/password fingerprints, unrelated fields, event identity and exact cleanup. Its native observations decide expected outcomes; unit doubles and source inspection alone are not native runtime proof. The old `tests/fixtures/status-switch.json` remains the oracle for accepted legacy execution.

The canonical operation identity is the semantics version. Keep the old SetValue descriptor, accepted field, compute and apply resolution internally for accepted work. Only its public discovery projection excludes Status; new controls discover `set_status` from the registry. No global compatibility mode, schema column or client-selectable legacy branch is added.

The legacy `_bulkcat_availability_off` record remains canonical JSON with `id`, `status`, `at` and `batch`; valid remembered statuses are publish, future, pending and private, bound to their own product ID. Its old SQL filter predicate remains unchanged, including its distinction from full record validation. It is not an authorization credential. Accepted legacy Draft operations save the old status; accepted legacy Published operations retain their original restore/conflict semantics. The existing legacy fixture specifies that table. New actions never create this record.

## 6. Bulk actions

Each action is a class implementing one interface: describe itself, validate its inputs, compute a result for one object without writing, apply that result. Preview and writer call the same computation, so what is previewed is what is written.

- **Set value** — native fields except new Status edits, or clear a nullable field.
- **Set Status** — the native publication target in §5.5; the legacy SetValue action remains internally resolvable for accepted work.
- **Increase or decrease** — price, stock quantity, weight or dimensions, by amount or percentage. Objects with no current value are skipped and counted.
- **Round** — to decimals, to the nearest step, or to a charm ending such as .95 or .99, up, down or to nearest. Rounding may run in the same action as an increase or decrease, because that is the common pricing job.
- **Copy regular price to sale price**, or back, optionally with a percentage discount in the same step, and **clear sale price**.
- **Find and replace** in name or SKU: plain text, optionally whole word, optionally case sensitive. No regular expressions in version 1, because a preview cannot make a bad expression safe for a non-technical owner. **Add prefix or suffix** to SKU.
- **Add or remove categories** and **tags**, leaving other terms alone. **Replace** sets the full list and says so in bold in the preview.

A batch holds an ordered list of at most twenty operations applied to each object in turn, so "increase regular by 12 per cent, then round to .95" is one batch, one preview and one undo.

Every action on a field a variation has its own value for carries **Also apply to variations** (the step argument `apply_to_variations`), starting from the shop's setting for the field's panel group — on for Publishing (status), off for Pricing and Stock, off for any other group (catalogue visibility belongs to the product, so it never reaches a variation) — and every action carries **Skip rows where the value is already correct**, on by default, so an unchanged product is neither re-saved nor logged.

### 6.1 External actions

A separately installed plugin, a **provider**, may register on the one action hook `bulkcat_register_providers` (fired once per request, the first time the action registry is built after `init`; the constant `BULKCAT_EXTENSION_CONTRACT` names the contract version, 1). It declares **external fields** — values it owns and stores, one per product or one per product and per variation, keyed `x_<provider>_<name>`, which the core never reads or writes itself — and **external actions**, each changing one of those fields. External actions appear in this bulk panel and in `GET /fields`, act on the same exact selection and go through the same preview, Apply, background job, History and undo; there is no second screen and no provider route. The provider computes each change without writing and supplies one absolute, idempotent, compare-and-set write per field; the core applies it, journals both values as opaque JSON with a plain-text rendering, and undoes by writing the old value back through the same write. In contract version 1 one change holds either native steps or the steps of one provider, never both (400 `bulkcat_mixed_change`). A missing, unavailable or incompatible provider never breaks the screen: its actions disappear or are disabled with a reason, a running job stops and says what it changed, history stays readable from stored text, and undo refuses with a plain reason until the provider returns. The contract, its interfaces, limits and lifecycle are in [EXTENSIONS.md](EXTENSIONS.md); [EXTENDING.md](EXTENDING.md) is the guide for writing a provider.

## 7. Category tree

`get_terms()` on `product_cat` with `hide_empty => false` and `update_term_meta_cache => true`, built into a nested array in PHP and cached in a transient keyed by the taxonomy's last-changed value, invalidated on `created_term`, `edited_term` and `delete_term`. Each node shows its own count and its count including descendants, from one grouped query rather than one per node, and counts respect the other active filters, so the tree doubles as a summary of the current result.

Selecting a node filters the grid; a toggle chooses *this category only* or *this category and its children*, defaulting to including children; Ctrl or Cmd click filters to several at once.

Re-parenting uses `wp_update_term()`, and a move that would make a term its own ancestor is rejected on the server as well as in the browser. **Sibling order is WooCommerce's own** (ticket 23, owner's ruling of 5 October): the tree reads and a move or reorder writes WooCommerce's `order` term meta, the value its own drag-reorder writes (`wc_set_term_order()`) and its shop and category screen sort siblings by (`meta_value+0` ascending, a category without one first, then by name), so a drag here changes the shop and WooCommerce's screen, and a drag there shows here at once (a change to that meta renews the tree cache). Only siblings' relative order matters to WooCommerce, so a move writes the category moved alone when it fits between its new neighbours, otherwise renumbers that parent's children from 1, writing only values that change, and fires `woocommerce_after_set_term_order` for each value written; the siblings it leaves keep theirs. A new category gets order 0, as WooCommerce's own screen gives it. The plugin's old tree-only order (`bulkcat_order`, 1.3.2 and earlier) is retired: never read or written again and never copied into the shop's order, so upgrading shows the shop's real order; the values stay stored (uninstall with data removal deletes them) and History keeps their old rows as "Old position in this screen only". **The default product category** (WooCommerce's `default_product_cat` option) carries `default: true` on its node and a Default badge; **Make default** (`POST /categories/{id}/default`, needing permission to edit that category as WooCommerce's own Make default does) sets it, journalled as `term_default` (old and new default ids) and undoable. Every term write is journalled and undoable like a product write. Only single-parent hierarchy is supported, because that is what WordPress taxonomies are.

## 8. Variations

Four rules govern variations everywhere.

1. **A parent never silently speaks for its variations.** Where variations disagree the parent cell shows a range or "Mixed" and is not editable in place.
2. **Selecting a parent does not select its variations.** **Also apply to variations** is what reaches them, and the preview states how many it adds.
3. **A field that does not exist on a variation is never offered on a variation row.** It is greyed with the reason, "Categories belong to the product, not to each variation", never silently hidden.
4. **Expansion is capped at 50 variations** with **Show all**.

A variable parent has no price of its own to set. Stock quantity applies only where that variation manages stock; a row that does not is reported as skipped with its reason rather than ignored. SKU uniqueness is checked across products and variations together, and a clash fails that row without failing the batch. After any variation write the parent's price range and stock summary are resynchronised through WooCommerce's own data store, never by writing parent meta directly.

A variation's native Enabled/disabled state is `publish`/`private`; it is not product publication or remembered restoration. Check the pinned native variation save handler separately from the product-editor publication capability. The manager continues to require edit permission on both the variation and its parent; a coarse native AJAX gate does not authorize weakening that boundary. In the pinned fixture the variation type maps `edit_post` to singular `edit_product`, unlike the parent's mapped product capabilities; test these actors separately. Draft/Pending are not writable variation states. Existing accepted legacy parent Off/On steps preserve their historical variation exclusion. New Status steps use the normal per-step **Also apply to variations** rule, independent of old records. Inline and drawer edits target only the named object.

A parent carries its variation count from a grouped count query, so variation rows are fetched only on expansion. **Also apply to variations** expands the selection when it is materialised, resolving each selected variable product to its published and private variations (menu order, then id), so the recorded batch contains every object it touched and the undo is exact. A variation the selection already holds is not added twice and keeps every step. An added variation carries only the steps whose switch is on, as its own item operation list. The parent keeps its row for the steps it takes, and is left out when it takes none — every step has the switch on and changes a price, which a variable product takes from its variations — so its row cannot only report a skip. A step with the switch on that meets a variable product without a value of its own is skipped, not failed, and a choice a variation cannot take (a status other than published or private) pushed down by the switch is skipped with its reason; chosen on the variation itself it fails. In **Variations only** mode nothing is expanded. The variations added count toward the 100,000-object limit. Parent-only fields are never pushed down, and variation-only fields never written to a parent. Attribute editing is version 2.

## 9. Preview, journal, history and undo

### 9.1 Preview

`POST /bulkcat/v1/preview` returns the computed sample and totals: matched, would change, already at target and would fail validation. With **Also apply to variations** on, `totals.by_type` splits products/variations; `variations_added` and `parents_left_out` explain expansion. `current_count` remains the exact selected count before expansion, including subsequently unavailable members. The writer's operation classes compute without saving products or terms. Above the existing 10,000-object computation cap, totals remain explicitly labelled estimates; this planning increment does not change that algorithm. The parts of an estimated total are scaled together, so they add up to the total they split (products and variations to the change count, legacy Off/On outcomes to theirs, the rows to theirs; T114).

New Status Results carry additive context: `requested_status`, `effective_status` and `scheduled_gmt`. Canonical operations keep the requested target; preview renders the predicted effective state. A genuinely already-effective state returns `already`, without saving. The legacy `availability` block, notes and context retain their historical interpretation for accepted work; new controls do not infer restoration from them. The internal password adapter preserves the exact native string, including punctuation, whitespace and backslashes; public text sanitization is unchanged. Password restoration is coupled to Status, guarded by the recorded expected password, and unavailable as a public writer. Pending replay checks the recorded actor before setters and again before saving; already-landed values settle from readback, denied unwritten values settle failed, and partial recovery never claims complete success. Internal password arguments, conflicts and legacy-record follow-up values are excluded or redacted from public samples, summaries, history and exports.

For new `set_status` only, preview binding includes every exact member's deterministic requested/effective status and relevant stored date, in canonical order, with an unreadable-member marker. It excludes the current clock value and raw passwords. Recompute at acceptance after receipt lookup; crossing from scheduled to immediate publication can require a fresh preview. No new Status step means an empty additive publication binding and byte-for-byte unchanged existing hashes. Accepted queued work uses native rules at execution time and journals the stored result.

Every bulk apply carries the preview hash, binding selection, operations and relevant settings. New grant-based bulk requests also carry an authenticated `scope_hash` covering expanded IDs, per-step assignments and unavailable members, including explicit-ID selections. For v2 snapshots the preview binds the current authorization epoch: live renewal preserves it; reauthorization after lease expiry requires preview again without changing membership. Accepted-request resolution precedes all selection/preview expiry checks (§12.6). Apply refuses 409 `bulkcat_preview_stale` on a changed scope, including a same-count substitution or newly added variation. It never re-runs a former filter. The v1 live-filter `preview_count`/`confirm_changed` escape is not part of v2; old tokens require reselection after upgrade. Missing/refused objects remain visible in scope/outcomes and cannot make a partial result claim full success. This is scope validation, not a lock on field values; the writer still checks current values and permissions. Detailed schemas/compatibility: [EXACT-SELECTION.md](EXACT-SELECTION.md).

### 9.3 Journal and audit log

The journal is written inside the same code path that saves the product, recording each touched field's before and after value with the object's `post_modified_gmt` at that moment. A status step on a product journals `status` and, when an accepted legacy operation writes its record or a new Status change clears an owned record (§5.5), a second row `availability_off` (**Status before Off**) holding the record's canonical JSON before and after, or '' for none; both rows come from the same save. The status journalled is the one WordPress stored, read back after the save. A native password effect is an internal coupled before/after change; raw passwords never appear in public preview, history or CSV. Validate every coupled write before applying any follow-up. **Manage stock and its coupled stock values:** when a change turns Manage stock off, WooCommerce's save clears the stock quantity, backorders and low stock threshold; when it turns it on, the save works the stock status out from the quantity. Each such change is journalled with its value before (backorders and low stock threshold as internal fields, `backorders` and `low_stock_amount`, never columns or bulk fields), its value after read back from the save. Untouched fields are not recorded, so the log stays proportionate to the change. Inline edits and detail-panel saves are one-item batches. Changes made outside the plugin are not recorded in version 1, and the screen says so.

### 9.4 Undo

Undo creates a batch with `source = undo` and `undo_of` set, whose operations are the recorded changes in reverse order, written back through the same CRUD path, queue and journal, with its own preview. Before reverting, the current value is compared with `new_value`; if they differ, and the current value is not already the `old_value` the undo puts back (as a cancelled undo leaves the objects it reached), the item is skipped and reported as "changed since this batch ran". The comparison is made when the undo is previewed, again when it is confirmed, and again for each object just before its chunk writes it (after the retry guard, so an object this undo already wrote is finished, never judged changed), for every field the batch changed (status and its record included): an object changed after the undo was confirmed is left alone whole, nothing written for it, with the same "changed since" sentence, unless **Revert anyway** was chosen. One object, one outcome: when the status step's own write-time check finds the status or its record changed since the plan (also under **Revert anyway**), the whole object is left alone the same way, its other fields included. An undo that puts nothing back (every object changed again first) does not undo the batch: it returns to the status it had and stays undoable, **Revert anyway** included, and the undo's result says so. The preview lists conflicts first, and **Revert anyway** is off by default. The result reports plainly: "12 of 1,284 were changed again after this batch and were left alone." A partial, failed or cancelled batch can be undone for the part that was applied. A regular and a sale price go back in the order that keeps the pair valid at each step (a regular price first when the sale price put back is not below the regular price the object holds), so undoing a change that cleared or lowered a sale price puts the original sale price back.

**Status and its recorded native effects undo together** (§5.5). New password effects participate in the same object-level conflict check and current publication permissions; old undo rows without a password retain their meaning. Never infer restoration from an ordinary new Status action. **Legacy status and its record** continue to undo together. The planner folds an object's `status` and `availability_off` rows into one internal step, `restore_status`, that no client may send (it is absent from `/fields`, and every public operation list refuses it as an unknown action). Conflicts are still per row: the current status against the status the batch left, and the current record against the record the batch left (listed as **Status before Off**). A product that carries its own record written by a later batch than the one being undone is also conflicted, "changed since", with the record as its current value; **Revert anyway** proceeds. These checks run when the undo is planned, at its preview and again at Apply; the step also carries the status and own record the object had then (`expected_status`, `expected_record`), and the runner checks them again when it writes the item, since a queued undo runs later: an object switched Off again, given another status, or with its record removed in between is skipped as changed since, with the same sentence, and nothing is written (the undo finishes partial and History still names who undid the batch). A step stored before these arguments existed is written as planned. `restore_status` takes the status it writes only from the journal, never from the record: the journal's old status is written through the Status field (a scheduled one as publish, left to WordPress's date rule). When the batch journalled the record, the record's old value is written back verbatim (id, status, time and batch unchanged; '' deletes it), so undoing an Off gives back the old status and no record, and undoing an On gives back draft and the original record. When the batch journalled only the status (a 1.0 batch, or an ordinary status change), a product that now has its own record keeps it if the restored status is draft and loses it otherwise, journalled. Undo of an undo plans `restore_status` again from the undo batch's own rows. History shows the record row as **Status before Off** with each value as the saved status and its time ("Published, saved 28 Sep 2026 14:03") or "—", never the JSON, and the History and audit CSV exports say the same.

**Manage stock and its coupled stock values undo together.** The planner folds an object's `manage_stock` row and its `stock_quantity`, `backorders`, `low_stock_amount` and `stock_status` rows into one internal step, `restore_stock`, that no client may send: Manage stock is written first, then the others, so the stock status WooCommerce works out on save follows the restored quantity. Putting back unmanaged stock writes only the stock status; WooCommerce empties the rest itself. Conflicts are still per row.

**Category changes undo through the same plan** (ticket 133 bug 1). A `term` object of a `tree` batch is planned by `Categories\TermUndo`: for each property the batch applied — name, slug, description, parent, display type, image, WooCommerce's sibling order (`term_menu_order`) and the default category (`term_default`) — the current value is compared with the value the batch left, a category changed since is conflicted ("changed since", left alone unless **Revert anyway**), and the step is the internal `restore_category` (`{ field, value }`), which no client can send. A category the batch created is removed again (`{ field: term_created }`) only while it has no products and no subcategories and is not the default. A parent or former default that no longer exists, and rows of the retired tree-only order (`term_order`), are skipped with a reason. The undo batch's `term` items are written by the chunk runner through WordPress's term functions, checked again just before each is written unless forced, and journalled under the same properties so the undo can itself be undone. Undo previews and summaries count categories apart (`by_type.term`, `by_type.categories`), so the dialog says "This puts 2 categories back as they were before." Delete and merge batches are never undone (§4.7).

**External changes** (§6.1) undo through the same plan: per object the core checks its own permissions, the action's capability and the provider's `authorise()`, reads the current value through the provider, converts an older journalled format through `upgrade()` (a newer one, or a failed upgrade, is skipped), lists a conflict when the current value is not the value the batch left, and plans the internal step `restore_external` (never offered or accepted from a client), which writes the oldest old value back through the provider's compare-and-set write. A batch whose provider is not registered is refused 409 `bulkcat_not_reversible` with `data.reason: provider_missing` ("This change was made with <add-on>, which is not active now. Turn it on again to undo this change."). One whose provider is registered but not available or incompatible is refused with `provider_unavailable` and the add-on's own reason after the core's words. History says which add-on it needs, and why when the add-on gave a reason. The refusal clears when the add-on can run again.

`POST /batches/{id}/undo` with `preview: true` returns the plan's counts (and `by_type`, the same counts for products and for variations apart, so the screen says what it puts back) and a page of its objects, conflicts first, with a `plan_hash`; applying sends the server-issued `uuid`/`request_proof` bound to its original batch, plan and force choice (§12.6), that hash (409 `bulkcat_preview_stale` when the plan has moved on since) and `force` for **Revert anyway**. The undo batch's items each carry their own operations (`bulkcat_batch_items.operations`), materialised before any work; the batch undone is `undoing` while it runs, `undone` once it completes or finishes partial, and back to its old status if the undo fails or is cancelled, or if it saved an object with only some of its values put back (one written, another skipped or failed), so the batch is never shown undone while a value is still missing. The history list shows reversibility from the cheap signals only (`conflicts: null`, no product read); so does the single batch read, which every open screen polls until a change finishes, unless asked with `reversibility=count`, which counts conflicts by planning the undo (T85). The plan is never held whole (T111): it is walked a page of objects at a time — the objects' order read first from the journal without its values, then each page's journal rows, products and plan, released before the next — while the counts and the hash are kept, the preview keeps only each object's id by state and plans its page again, and the undo batch's items are recorded a chunk at a time as the walk hands them over, its header completed at the end, all in the acceptance transaction. So preview, counting and confirming an undo fit a web request's memory for any change a selection can hold (100,000 objects), and the screen offers undo for every change, whatever its size. Planning reads every object the change touched (about two minutes for 100,000), so these requests lift PHP's time limit where the host allows, as exports do. An undo batch's summary carries `by_type`, how many products and variations it puts back.

### 9.5 Retention

`bulkcat_history_retention_days` defaults to 90, adjustable between 7 and 730, or kept indefinitely. A daily action, `bulkcat_prune_history`, removes item/journal details past the limit in bounded chunks, retaining batch headers. A pruned batch stays in the list, marked no longer reversible. Running batches are never pruned. Planned Apply/undo request receipts stay as long as their headers, independently of selection cleanup and this undo-retention setting. A future header-removal path must leave a gone receipt through at least grant issuance plus eight days; later retries are still rejected by the signed acceptance deadline (§12.6).

## 10. Saved views and export

**Saved views.** The DataViews view object plus the category selection is saved by name in the `bulkcat_views` user meta as JSON. Views can be duplicated, renamed and reordered, and one marked as the default the screen opens with. They are per user, not shared in version 1.

**Export.** A CSV download of chosen rows and the view's columns. It is a read, generated on request, streamed in pages so memory stays flat, and stored nowhere. Rows come in ascending ID order: a filter export walks its matches by ID, each page starting after the last ID written, so a row whose sort key changes, or a product added, while the file is written is never written twice or left out. **Export** opens a small dialog.

*Rows.* **Selected**, the default whenever anything is selected, is the exact selection (§3): every selected product and variation once, including those outside the current results, in ascending ID order, and nothing else. A product's variations come only when they are selected themselves, and nothing that matches later is added. **All matching the current filters** is every row matching the view's search, filters, category and mode when the file is made, in the view's sort order, not only the current page. With nothing selected, **Selected** is unavailable and reads "Nothing selected". With no search, filter or category active, the second choice reads **The whole catalogue** with its count and needs an explicit confirmation, which the server also requires. The server decides this on the conditions as parsed, not as sent: no filter, a blank search and no parent restriction, in any mode, so an argument sent empty cannot bypass it. A selection is never widened or narrowed by a filter and never needs the confirmation, however large it is. A selected item that no longer exists, is in the bin or in a status the catalogue does not list, is not a product or variation, or is a variation whose product is gone or no longer listed, is left out and counted; nothing of it is read, and the file holds no placeholder rows. Before the download the dialog states how many rows the file will hold and how many selected items are left out.

*Columns.* The name, then the visible columns in the order the column chooser shows them, with the image left out. There is no second field picker. With the switch below off, the header and every cell are exactly what the export wrote before the dialog existed.

*Identifiers for re-import.* A switch, off each time the dialog opens, puts **ID**, **SKU**, **Parent** and **Type** first. These headings are English whatever the site language, as WooCommerce's product importer maps them. Parent follows WooCommerce's own exporter: for any item with a parent post (a variation's product, or a product that has a parent) it is the parent's SKU, or `id:` and the parent's ID when the parent has no SKU or its SKU would not read back unchanged (it would carry the formula guard below, WooCommerce's text cleaning would change it, or it is `0` or looks like `id:` and digits); it is empty when there is no parent, or the parent is not a product or variation. Type is the product type followed by `downloadable` and `virtual` where they apply, as WooCommerce's own export writes it, because the importer resets both flags from it. A visible column that is one of these is not repeated. While the switch is on, every other column keeps its values, but its heading gains "(for reference)" unless the importer round trip proves it reads back unchanged or the importer does not map it, so the importer never maps such a column by default: in version 1, categories, tags and shipping class, which are written as IDs, and the rendered price. A column added later is "for reference" until the round trip proves it. The file then goes back through **Products → Import** with *Update existing products*. That import belongs to WooCommerce, not to this plugin, so it is not in History and cannot be undone here (§2).

*Format.* UTF-8 with a byte-order mark, every field quoted, CRLF line endings, and the separator from Settings (§11). With the identifier switch on, the first heading, `ID`, follows the byte-order mark unquoted: PHP's CSV reader, which WooCommerce's importer uses, reads a quoted field that follows a byte-order mark with its quotes (`"ID"`), which the importer would not map, so every row would be matched by SKU alone. A field beginning, after any spaces, with `=`, `+`, `-` or `@`, or beginning with a tab or carriage return, is prefixed with an apostrophe so a spreadsheet does not treat exported data as a formula (§13). This guard is stricter than WooCommerce's own and is not relaxed for re-import. WooCommerce's importer does not remove that apostrophe from a SKU or a name, and it cleans a SKU of line breaks, repeated or edge spaces, tags and `%` codes, so while the switch is on the dialog warns, with a count, when rows have a SKU the importer would not keep as it is, and when rows have a guarded name.

*File name.* `catalogue-selected`, `catalogue-filtered` or `catalogue-all` (a confirmed whole catalogue), with `-with-ids` when the switch is on, then the site's date and time: `catalogue-selected-with-ids-2026-10-05-1432.csv`. No request value enters the name.

*Transport and limits.* The catalogue export is `POST /export` (§12.1), posted into a hidden frame so a large file streams to disk. The nonce and the selection token travel in the body, never in a URL, the page history or a log; a token in the query string is refused. An export resolves a selection exactly as preview does and never renews, extends or releases it: a lapsed lease asks for the selection to be restored, a selection past its retention is gone, another user's or an altered token gets the uniform refusal, and a 1.0 token asks for the products to be chosen again. Explicit IDs, for API callers, are at most 1,000 and never combined with a token. Every refusal is a plain sentence sent before any CSV byte. The export writes nothing: no grant, receipt, lease, retention, selection, product, term or option, apart from the grid's own count cache. Just before streaming it lifts PHP's time limit where the host allows; a web-server or PHP-FPM timeout still applies, so on such a host a very large export is narrowed with a filter or a smaller selection.

History and audit rows export the same way, through `GET /export` and their own columns (§4.6). `GET /export` does not export the catalogue: a request from a page loaded before the dialog is refused with a sentence asking for a reload.

## 12. Engine

### 12.1 REST

Routes are registered under `bulkcat/v1` with `register_rest_route()`. Every route declares an explicit `permission_callback`; none returns `true`. Authentication is the logged-in cookie plus the `wp_rest` nonce through `apiFetch`'s nonce middleware. There is no REST API key or application password path, and no request outside the site. The plugin does not extend the WooCommerce REST namespace.

The routes are `/fields`; `GET /products` returning `{ items, pagination: { page, perPage, total, totalPages } }`; `PATCH /products/{id}`, recorded as a one-item batch and answering `{ item, batch_id, status, results }` — the updated row in the `/products` item shape, the batch's id, its final status (complete, partial or failed) and one result per step; `GET /products/{id}/variations`, returning `{ items, pagination }` in WooCommerce's variation order with each variation's parent name and attribute summary, and 404 for an id that is not a product; `POST /selection`, capturing an exact set with a signed owner-bound token; `POST /selection/compose`, `/selection/inspect`, `/selection/renew` and `/selection/release`, plus `POST /requests` for signed request grants and `/requests/resolve` for durable outcome lookup, as defined in [EXACT-SELECTION.md](EXACT-SELECTION.md#api); `POST /preview`; `/batches` to queue and to list, `/batches/{id}` for live progress, `/batches/{id}/changes`, and `/batches/{id}/cancel` and `/undo`, the latter accepting `force`; `/audit`; `/categories`, `/categories/{id}` and `/categories/{id}/move`; `/views` and `/views/{id}`; `POST /export` for the catalogue: the rows (a selection token, at most 1,000 IDs, or the `/products` filter arguments, with `confirm_all` for an empty filter), `columns[]`, `identifiers`, and `summary` for the dialog's counts, answering `{ rows, left_out, guarded_identifiers, guarded_names, whole_catalogue, filename }` without streaming; the nonce and token go in the body, never in a URL; `GET /export` for history exports; and `/settings`.

With at least one provider registered (§6.1), `/fields` also lists each external field (`type` and `source` `external`, with its `provider`; the grid, filters, inline editing and detail panel ignore it), each external action after the native ones with `provider`, `variations`, `available`, `unavailableReason`, `alwaysConfirm` and `confirmReason`, the providers' chooser groups after the native groups, and `providers` (`id`, `label`, `version`, `available`, `reason`); with none, the payload is byte-identical to 1.0's. External limits: 5 fields, 20 actions and 2 chooser groups per provider, 500 choices per argument, at most 100 items chosen in one multichoice argument, labels 80 characters, descriptions 300, reasons 255, 3 preview notes of 200, described values 1,000, and 64 KB per encoded value. An external value sent to `PATCH /products/{id}` is refused 400 `bulkcat_external_not_inline`.

`/products` accepts paging with `per_page` capped at 100, `search`, `orderby`, `order`, `mode`, `fields[]` and one argument per filter in §4.1. Every argument is generated from the registry with its own type, sanitise and validate callbacks, so a malformed or unknown parameter is rejected before any handler runs. New bulk batch bodies carry the server-issued `uuid` and `request_proof`, the preview's `preview_hash` and authenticated `scope_hash` (§9.1). Capture, compose and queued undo also use these grants. Issuance/resolution use current cookie/nonce/capability checks and do not write catalogue data. Unknown legacy bare UUIDs cannot create work; existing legacy UUIDs follow the conservative retained-header resolution in §12.6. Other limits: 20 operations per batch, 100,000 objects per selection (the variations **Also apply to variations** adds included), 100 terms per term operation.

### 12.2 Reads

Reads never instantiate `WC_Product`; building 100 product objects per page costs hundreds of queries. A query builder produces one prepared `$wpdb` statement against `wp_posts` joined to `wc_product_meta_lookup`, adding `wp_term_relationships` joins only when a taxonomy filter is present, and returning identifiers and sort keys only. The lookup table carries SKU, minimum and maximum price, stock status, stock quantity, rating and total sales, covering most sorts and filters without touching `wp_postmeta`.

Those identifiers are hydrated in a fixed number of queries regardless of page size: `_prime_post_caches()`, `update_meta_cache()` for the visible columns' meta keys, one `wp_get_object_terms()` across `product_cat`, `product_tag`, `product_visibility` and `product_shipping_class`, and one grouped variation-count query.

Counts are a separate `COUNT(*)` on the same conditions, cached 60 seconds in a transient keyed by a hash of the filter, because `SQL_CALC_FOUND_ROWS` is slow and deprecated in MySQL 8. No query is issued without a `LIMIT`; column and table names come from an allow-list; nothing from a request is interpolated into SQL; no index is added to a core table. The direct database access here is deliberate and annotated, with results cached in an object-cache group invalidated by the products' last-changed value, and the tree by the taxonomy's.

### 12.3 Writes

Writes go through WooCommerce CRUD — `wc_get_product()`, typed setters, `save()` — never direct SQL and never `update_post_meta` for a product field, which keeps the lookup table, term relationships, transients and the `woocommerce_update_product` hook correct for every other plugin on the site. Term changes use `wp_set_object_terms()` and `wp_update_term()`.

Each chunk runs inside one Action Scheduler action in the `bulk-catalogue-manager-for-woocommerce` group (the full slug, so no other plugin can share it), wrapped in `wp_defer_term_counting( true )` and flushed at its end. Each object is loaded, each operation applied in order, before and after journalled, and the object saved only if something changed. A failure marks that item failed and does not stop the chunk. Chunks are idempotent. Just before `save()` the writer records an intent row per changed field (result `pending`, holding the computed new value) and settles it to `applied` or `failed` once `save()` returns or throws. A retry that finds settled rows for an object skips it; one that finds intent rows — the run died after WooCommerce saved but before the journal caught up — computes nothing again, but writes each recorded absolute value, or leaves it where the object already holds it, and settles the rows. So a retry after a timeout cannot double-apply a percentage increase, even when the timeout struck inside a slow save hook. An intent row left unsettled (the batch was cancelled before a retry) is planned by undo like an applied one.

### 12.4 Scheduler

Action Scheduler ships inside WooCommerce and is used through its public `as_*` functions only. The plugin does not touch WooCommerce's internal batch-processing classes, which carry no backwards-compatibility guarantee.

The model is a chain, not a fan-out, because Action Scheduler's default concurrency is one. Creating a batch enqueues one `bulkcat_run_chunk` action through `as_enqueue_async_action()`; each run claims the next chunk of pending items with a locking update, processes them, updates the counters and enqueues its successor if items remain. A claim is released after a timeout and retried up to three times. Each claim schedules its own retry six minutes ahead (the five-minute lease plus one minute), unscheduled when the chunk ends normally, so a chunk killed mid-way is picked up without anyone watching; a claim older than five minutes is stale and the next run takes its items over. So that a slow run whose lease went stale never works the same items as the run that took them over, each item is claimed again on its own just before it is written (`state` from `pending` to `working`, only while the chunk's `claim_token` is still the run's); an item the run no longer holds is skipped, neither written nor marked, and a `working` item whose claim has gone stale is put back to `pending` for the next run. Past 80 per cent of the lease a run claims no further item and releases the rest of its chunk to its successor. This survives a crash and gives accurate progress without scheduling hundreds of actions up front.

Default chunk size is 50 products or 100 variations (the settings *Products per background batch* and *Variations per background batch*), floor 10, ceiling 100, each filterable through `bulkcat_batch_size`, which receives the size, the batch id and the kind, `product` or `variation`. A chunk holds one kind: products (and category items) while any is left to claim, up to the product size, then variations, up to the variation size, so a mixed batch counts its variations against the variation size. A chunk using more than 70 per cent of the PHP time limit halves the size for the rest of the batch and records why; the batch records the product size and the variation size follows it in proportion, so both halve and grow back together. With no PHP time limit (WP-CLI, some cron runners) the lease stands in for it. Background work checks every object, each variation and its parent too, against the batch's recorded user before writing it. Cancelling sets the status and the next run exits without claiming; applied chunks stay applied and the batch remains undoable. The queue runner is not reconfigured on the owner's behalf — `action_scheduler_queue_runner_batch_size` and `_concurrent_batches` are left alone — and chunk size is the only knob.

### 12.5 Performance targets

On 20,000 seeded products and 70,000 variations, PHP 8.3, MySQL 8, no persistent object cache. Asserted in the performance suite, not left as intentions.

- Grid page of 25 rows with three filters: 95th-percentile server time under 400 ms, no more than 20 queries, constant with respect to page size.
- Grid page of 25 rows with three filters in products-and-variations mode: 95th-percentile server time under 750 ms, filtered count under 1 second cold, the same query limit. Measured 514 ms p95 and 669 ms cold on a loaded host (T76, `tests/probe/PERF.md`). The mode lists products and their variations together, so three non-selective filters match most of 90,000 rows, and sorting them by name has no index on `post_title` to use (§12.2 adds no index to a core table); the work grows with the matches, not the page.
- Filtered count under 500 ms cold, category tree under 300 ms cold, whole-catalogue selection resolved under 5 seconds.
- At least 300 products a minute written at the default chunk size, peak memory under 96 MB per chunk.
- CSV export of 20,000 rows, by filter or by selection, with or without identifiers: first byte under 2 seconds, complete under 60 seconds, memory flat, and a fixed number of queries per page whatever its size. A 100,000-member selection streams to completion under a 128 MB memory limit. Built JavaScript under 400 KB compressed, loaded only on this screen.

### 12.6 Failure modes

- **Partial failure.** The batch finishes as *completed with errors*, each failure listed with its reason. The successful part is journalled and undoable on its own.
- **Timeouts.** A chunk killed mid-way leaves completed objects journalled and its chunk row incomplete; the retry continues with the remainder. Chunk size is bounded to fit a conservative execution limit.
- **Concurrent edits.** Batches touching the same product are serialised by the queue's single concurrency. A product edited in the native editor is not locked; the journal records the value immediately before the plugin's write, which is what undo needs.
- **Undo conflicts.** Reported, not overwritten, unless **Revert anyway** is chosen.
- **Stale selection.** Frozen membership never gains new matches. Missing/revoked objects remain reported; changed expansion requires preview again. Expired authorization is renewable under current permissions while exact membership is retained (seven days since creation/authorized keepalive). Reauthorization rotates the epoch and requires fresh preview. Only genuinely pruned membership requires explicit reselection; never silently replay its old filter. Best-effort release bounds unreferenced intermediate payloads to one hour, with seven-day inactivity cleanup if release is lost. Late responses after Clear cannot restore discarded selection. Partial/failed/cancelled jobs retain recoverable scope; full success clears only submitted scope, preserving later intent (EXACT-SELECTION.md).
- **Abandoned inline edit.** An inline batch is written in the request that opened it; if that request dies, the batch stays running with no runner behind it. The next read of it after ten minutes without activity marks it failed, its unwritten item failed with a plain reason, and says why in its note.
- **Provider unavailable** (§6.1). Preview and a new Apply answer 409 `bulkcat_provider_unavailable` with the add-on's reason; an accepted Apply still resolves by its receipt. Before claiming, every chunk of a batch with external steps checks each provider its manifest names — registered, available, contract-compatible and able to read each recorded format. If not, it claims nothing, skips every still-pending item with a plain reason, and the batch ends through the ordinary final-status rule, never `complete`. The note is "Stopped because <add-on> is not active. N products were changed; the rest were left alone." when the add-on is not registered, or "Stopped because <add-on> cannot run. N products were changed; the rest were left alone. <its reason>" when it is registered but cannot run. Nothing resumes on its own; the retained selection lets the owner preview and apply again once the add-on is back. Applied rows and intent rows stay for undo.
- **Scheduler stalled.** If the queue has not run for five minutes while a batch is pending, the screen says so and points at the scheduled actions tool rather than showing false progress; the batch applies nothing.
- **Duplicate submission (built on the exact-selection branch, T81–T83; the screen moves to it in T84).** The 1.0 60-second replay cache and age-limited database fallback were insufficient for delayed retries and are gone. New capture/compose/Apply/undo requests use a server-issued, non-renewable UUID/proof with a signed 24-hour acceptance deadline and an immutable canonical fingerprint. Resolve durable owner/UUID/fingerprint receipts before selection authorization, payload retention, preview freshness or grant deadline checks and before creating any header. Matching retries identify the original result; altered input returns 409. Unique receipt claim, result/header/items and acceptance commit atomically before idempotent scheduling; rollback, ambiguous commit and post-commit scheduling failure never trigger a new UUID or a duplicate batch. Selection receipts/gone tombstones last eight days from issuance; Apply/undo receipts last with their batch header (§9.5). After receipt cleanup, expired signed grants still refuse new acceptance. A 60-second cache can only accelerate durable lookup. Unknown bare legacy UUIDs require reload; known legacy headers are checked without an age cutoff and ambiguities refuse, preserving existing jobs/history. See [request lifecycle, migration and regressions](EXACT-SELECTION.md#request-identities-and-durable-replay).

## 13. Security

- Page and read routes require `manage_woocommerce`, filterable through `bulkcat_capability`, or `manage_options` under the administrators-only setting; category writes `manage_product_terms`, plus the per-term capabilities core checks — `edit_term` on the category edited or moved, the taxonomy's `edit_terms` to create one; settings writes `manage_options`.
- Write routes also require `edit_products`, and every object is checked with `current_user_can( 'edit_post', $id )` before it is written, honouring `edit_others_products`; a variation also needs `edit_post` on its parent, whose price range and stock its save resynchronises, and a change to categories, tags or shipping class needs the taxonomy's `assign_terms` (`assign_product_terms`). A product the user may not edit is skipped and reported, never silently dropped. An undo plan checks the person undoing, not the batch's original author.
- New publication requires the native transition-specific publish capability as well as object edit permission. Editable Published/Future resaves are not blanket-denied for lacking `publish_products`. A denied new publish is reported rather than silently elevated; the native editor may instead coerce it to Pending or retain its old state. Variation enable/disable uses its native capability model plus the manager's parent/object edit gates. Inspect native behaviour before declaring a permission defect; source-only possibilities are not proven exploits.
- Check publication permissions again immediately before save/replay for the recorded actor (`null` means current requester; explicit actor uses `user_can`; actor 0 is never elevated). A revoked actor cannot start another write. An already-landed write settles from truthful readback without requiring a new write. Do not call the private form translator or change global POST/current user in REST/worker runtime code.
- Background work runs with no current user, so each chunk re-checks every object against the batch's recorded `user_id` with `user_can()`. A batch cannot give its initiator more rights than they had at queue time, and an item whose permission was revoked is skipped and recorded.
- `wp_create_nonce( 'wp_rest' )` is localised at page load and refreshed through the Heartbeat API; a `rest_cookie_invalid_nonce` response triggers one automatic refresh and retry before the application reports an error.
- Input passes the registry's sanitiser and validator. All SQL uses `$wpdb->prepare()`, with interpolated identifiers cast to integers. PHP escapes at output, the JavaScript renders text as text, and `dangerouslySetInnerHTML` is never used. A name written without `unfiltered_html` passes through `wp_filter_post_kses`; in background work that is the batch's recorded user's `unfiltered_html` (`user_can()`), as in their own edit, and a category name or description follows the user its batch is recorded for. Unexpected errors are written to the WooCommerce log and never returned to the client.
- **External actions** (§6.1) add layers that can only narrow: the screen's capability, then each action's own capability (`user_can()` for the requester at `/fields`, grant issuance, preview and acceptance, for the batch's recorded user on every chunk, and for the person undoing), then per object the core's edit check and the provider's `authorise()`. A refused object is skipped and reported. Every provider string is plain text: tags and control characters are stripped and long strings trimmed, and the screen renders text only. Raw external values never appear in a response or an export. Provider code is code an administrator installed; the contract guards against accidental bypass and unsafe output, and does not claim to sandbox it.
- Export applies the formula-injection guard in §10. A selection export reads only products and variations, and only from the requester's own selection. No external HTTP request, no remote asset or font, no public route, no data collected.

## 14. Accessibility

The target is WCAG 2.2 AA, verified rather than asserted.

- A real table with a caption, sort state in `aria-sort`, and the product name cell as each row's header. Selection checkboxes carry the product name in their accessible name, not "select row".
- Everything is operable by keyboard alone, including the whole path from filter to preview to apply to undo. Arrows move between cells, Enter begins an inline edit, Escape cancels, Tab leaves. The slide-over and dialogs trap focus, close on Escape and return focus to whatever opened them.
- The category panel is an ARIA tree with roving tab index, arrow keys, Home and End, and type-ahead; every drag has the **Move to…** dialog as its keyboard equivalent.
- Progress is announced politely through `wp.a11y.speak` at milestones rather than every tick, the result once, errors assertively. Switches carry the product in their accessible name, so a screen reader says "Shown in shop and search, Blue Widget". An ordinary Status edit uses the same Enter/blur commit and Escape cancel as other inline fields; its saved announcement and displayed row use the server result.
- Colour is never the only signal; every status is a word as well as a badge. Text meets 4.5:1 and components 3:1 in both admin colour schemes, targets are at least 24 by 24 pixels, focus appearance meets the 2.2 criterion, and animation respects `prefers-reduced-motion`.
- Usable at 320 pixels wide and at 400 per cent zoom, the panel collapsing to a control, and every control has a visible label.

## 18. Open questions

1. Should inline edits be journalled individually, as specified, or coalesced per editing session?
2. May any user with the capability undo another user's batch, or only their own?
3. Should pruning hard-delete history, or write it to a CSV first?
4. Are both the table and grid layouts worth shipping, or is the table alone enough to learn?
5. Should term writes and product writes share one batch type, as specified, or have separate undo paths?

### 18.1 Working defaults

Each answer below is a **working assumption until the owner answers**. It records what version 1.0.0 does, so the code, the docs and this specification agree; an answer from the owner that differs replaces it here first and then in the code.

1. **Inline edits are journalled individually.** Each inline edit and each detail-panel save is its own one-item batch, written in the request through `Engine\InlineWrite`, listed in History and undone on its own (§9.3). Nothing is coalesced per editing session. *Working assumption until the owner answers.*
2. **Any user with the capability may undo any batch.** Undo needs the write capabilities of §13 (`Access::can_write`), and the plan checks the person undoing against every object, not the batch's original author; there is no own-batches-only rule. *Working assumption until the owner answers.*
3. **Pruning hard-deletes.** Past the retention limit the daily prune deletes a batch's `bulkcat_changes` and `bulkcat_batch_items` rows; the batch row stays listed as no longer reversible (§9.5). No CSV is written first: an owner who wants a copy exports it beforehand through History's CSV export (a batch's changes, the audit log or the batch list). The History panel states the retention period and the Settings tab where it changes. *Working assumption until the owner answers.*
4. **Both the table and grid layouts ship.** Table is the default and the layout the design targets; the Table | Grid switch offers the grid as a second layout of the same view (§4.1). *Working assumption until the owner answers.*
5. **Term writes and product writes share one batch type.** A category create, rename or move is a batch like a product change (source `tree`, items of `object_type` `term`), journalled in `bulkcat_changes` and undone through the same undo path and History (§7, §9.2). *Working assumption until the owner answers.*
