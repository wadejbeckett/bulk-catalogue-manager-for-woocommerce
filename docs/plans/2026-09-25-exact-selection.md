### T83 engineering rulings (28 September)

The contract left these open; each takes the conservative option.

- **Canonical intents are never normalised again.** Issuance runs the operation list through the registry once and returns it with every default written out; a submitted canonical intent is only shape-checked (exact keys, sorted unique ids, one to twenty `{ action, args }` steps, digests), so its fingerprint is exactly what was signed and a later settings or registry change cannot stop an accepted request resolving. Before a new acceptance, `BatchIntent::current_operations()` asks the registry again: a refusal is returned, a different normalisation is `bulkcat_preview_stale`, and otherwise the registry's own list — never the shape the client sent — is what the scope, the preview hash and the recorded batch use (the fingerprint sorts map keys, so it cannot tell a list from a map with the same numbered keys, or one key order from another; review finding, 28 September).
- **`bulkcat_batch_created` fires on the durable path** (it is a documented public hook): once, after the acceptance transaction commits and after the batch's chunk is queued, for the request that committed it; never on a replay. Scheduling never depends on it: `BatchRecovery::finish()` queues the chunk (`ChunkRunner::ensure_queued()`) first on acceptance and again on every replay, so a listener that throws cannot hold the batch back (the request answers 503 and its retry replays the queued batch). A crash between the commit and the action leaves the batch scheduled by the next resolution without the action firing; it can never fire twice.
- **A 1.0 screen cannot create work.** A bare `uuid` on `/batches` or `/undo` is resolved against the user's batch headers at any age (`BatchFactory::earlier()`): none is 409 `bulkcat_legacy_request` asking for a reload (empty `batch_ids`); exactly one that is the same request (same operations and ids or v1 filter conditions; for undo the same batch, plan hash and force) is its 200 replay; anything else is 409 naming the owner's batch ids as History references. Consequence: the unchanged 1.0 screen on this branch can preview explicit ids but cannot Apply or undo until T84 sends grants; the branch is not releasable between T83 and T84.
- **`BatchFactory::create()` / `create_undo()` stay as the trusted internal engine API** (no REST caller since T83; tests and probes use them). The 60-second transient and the create-then-discard race guard are gone; the any-age lookup runs before anything is written. The `bulkcat_batch_request_` prefix stays registered so uninstall still removes 1.0 transients.
- **Every preview is exact.** Explicit ids are sorted and deduplicated; `totals.matched` counts unavailable members — deleted, in the bin, in a status the list does not show, or changed in kind — which stay in the scope and are recorded as items **already failed** with a plain reason at acceptance (`BatchFactory::record_scope()`, `BatchRepository::fail_objects()`, counted done and failed), so they are never claimed or written, even if the object is restored before the chunk runs, and such a batch ends `partial` or `failed`, never `complete` (review blocker, 28 September: items for members in the bin had been written). A scope whose members are all unavailable is still recorded rather than silently refused. 1.0 transient tokens are refused on preview with the reselect refusal.
- **An object's kind is checked at write time.** `Writer::write()` takes the item's kind; an object that became a variation or a product since it was chosen fails with `bulkcat_changed_kind` and is not written. The preview never loads an unavailable scope member.
- **The preview shows nothing of an object the user may not edit**: every step is skipped with the permission reason, with no name, current or new value, and no warning is counted from it.
- **Scheduling:** `ChunkRunner::ensure_queued()` checks and enqueues under a per-batch MySQL named lock (`BatchRepository::with_schedule_lock()`), because Action Scheduler's unique enqueue lets two concurrent inserts through; when the lock cannot be taken (named locks refused, or held past ten seconds) it runs unlocked rather than stop scheduling — a duplicate chunk action is harmless because items are claimed one by one. A pending delayed retry of the batch counts as queued, so resolving a request never cuts the retry back-off short. If a unique enqueue is refused while nothing is queued for this batch (an Action Scheduler whose uniqueness ignores arguments), a plain enqueue follows. `BatchRecovery::finish()` reads the batch strictly: a failed read is a retryable 503, never a silent skip. Accepted as harmless (review note): `finish()` reads the status outside the lock and `ensure_queued()` does not re-check it, so a batch finishing at that instant can get one extra chunk action, which finds nothing to claim.
- **Refusal wording:** a malformed Apply or undo intent or envelope is 400 `bulkcat_invalid_value` in the words of a change ("This change could not be read. Reload the page, preview the change again, then apply it."), not the selection wording capture and compose use.
- **The durable batch header's selection summary** records unavailable members as a count (the items hold their identities) and the snapshot id, never a whole-ID list for a snapshot.

### T84 screen rulings (28 September)

Where the contract left a screen choice open, or the delivery brief and the contract differed, the simplest option that matches the prototype was taken:

- **Clear search clears the search and the selection** (SPEC §4.1, EXACT-SELECTION "Behaviour", the Wayfinder ruling); **Clear selection** clears only the selection. The search chip's button is the deliberate Clear search; editing the search box, including DataViews' own clear button and typing through empty text, is not. **Clear filters** remains a filter action and keeps the selection. The delivery brief's phrase "Clear search … clears only the search" contradicts the three accepted sources and was not followed.
- **Reload recovery uses the tab's `sessionStorage`**, holding the opaque handles, the counts shown and, while an intent is unconfirmed, that intent's own arguments (the ids ticked or unticked, or the view's query) with its grants — never a snapshot's membership — under the site root and user, removed on Clear or when nothing is held. *(Corrected in T85: this line said "never ids", which was not so for a pending intent; `selection-session.test.js` now pins what is kept. Confirmed by Main Build on 28 September.)* The contract rules out local-storage recovery and cross-session loading, and keeps handles "in memory"; a tab's sessionStorage ends with the tab, so it is the smallest store that lets a reload, or a tab the browser discarded while suspended, return to the same selection, as the brief asks. For review.
- **The bar's actions stay available while the selection is saving**; the panel reads the live selection and holds Check the change with the reason until it settles, so a quick keyboard Make a change is not lost. Only Apply and preview wait, as the contract asks.
- **Review selected products is a slide-over** in the details drawer's style (the prototype has no review): counts by type, 25 a page, Remove on every row, unavailable members as "No longer available" without details, Escape and focus return.
- **The bar's count is always "N products (and M variations) selected"** from the server's `count`/`by_type`; it never says "all matching these filters", since a snapshot outlives the view. The page line and "Select all N … matching these filters." keep T75's wording; the offer is hidden while the view's conditions are the ones last added.
- **Grants for Apply and undo are held for the screen** (module level), not for one opening of the panel or one drawing of a History card, so closing and reopening after an uncertain answer still resends, or first resolves, the same grant. A reload loses an uncertain Apply grant (the receipt still guards the server; History shows the outcome) — T85 follow-up.
- **The Done step keeps the scope it applied**, since the live selection is cleared when the change finishes.
- **Notice actions go through Notice's `actions` and a string `spokenMessage`**: `@wordpress/components` Notice renders element children to a string for its announcement, which runs the buttons' hooks inside it; a notice changing from plain text to one with buttons crashed the screen on the fixture (found by the browser journey, fixed and pinned by a Jest regression).

## Review corrections and stopping point

The 25 September engineering review found three lifecycle gaps: pruning the sole snapshot receipt could permit recapture; the existing 60-second Apply deduplication cannot cover delayed uncertain retries; and authorization expiry alone must not discard a suspended open tab's selection. T81–T85 now specify independent durable receipts, bounded signed acceptance, and reauthorization of retained exact membership. These corrections refine the accepted workflow, without new business scope.
